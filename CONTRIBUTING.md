# Совместная работа

## Роли

Роль описывает ответственность, а не должность. Один человек или агент может
выполнять несколько ролей, но у каждой задачи один владелец.

| Роль | Отвечает за | Проверяет перед передачей |
| --- | --- | --- |
| Product owner | пользователь, бизнес-метрики, приоритеты | задача даёт измеримую пользу |
| Архитектор | контракты, границы модулей, router | совместимость и путь отказа |
| Data engineer | ingestion, schema, preprocessing, provenance | hashes, пропуски, дубли, leakage |
| Аналитик/разметчик | инструкция, gold, срезы | независимость и согласованность меток |
| NLP/ML engineer | rules, encoder, verifier | quality delta на фиксированном split |
| LLM engineer | prompts, structured output, бюджет | evidence, retries, цена и отказ |
| Backend engineer | CLI, API, batch, errors | контракт, limits, idempotency |
| QA | тест-дизайн, негативные сценарии | регрессии и воспроизводимость |
| MLOps/release | VM, конфигурация, наблюдаемость | тот же SHA, health, rollback |
| Technical writer | README, ТЗ, отчёты | команды работают, цифры имеют источник |
| Интегратор | review, merge, релиз | нет конфликтов, долг записан в TASKS |

## Жизненный цикл задачи

```text
BACKLOG → READY → IN_PROGRESS → REVIEW → DONE
                         ↘ BLOCKED
```

### Claim

```bash
git fetch work
git switch -c eval/eval-001-independent-gold work/main
# изменить только строку задачи в TASKS.md
git add TASKS.md
git commit -m "chore(tasks): claim EVAL-001"
git push -u work HEAD
```

Если общей веткой стала другая, её фиксирует интегратор в `TASKS.md`.
Claim содержит дату начала и реальное имя/псевдоним владельца.

### Реализация

- Коммиты маленькие и содержат одну логическую правку.
- Код не читает реальные ответы из `data/gold` во время inference.
- Конфигурация версионируется; секреты и данные — нет.
- Эксперимент получает ID, Git SHA, hashes входов, параметры и manifest.
- Значения метрик сопровождаются split, числом карточек и происхождением gold.

### Передача в review

В PR должны быть:

1. задача и ожидаемый эффект;
2. список изменённых модулей;
3. команды проверки и их фактический вывод;
4. до/после для качества, стоимости или надёжности;
5. риски и способ отката;
6. обновлённые `TASKS.md` и `docs/PROJECT_STATUS.md`.

Автор переводит задачу в `REVIEW`. Reviewer не должен быть автором изменения
gold или метода, если PR заявляет независимую оценку качества.

### Merge

Интегратор убеждается, что изменения основаны на актуальном GitHub `main`,
проверки прошли и цифры воспроизводимы. После merge workflow публикует тот же
commit в Gitea `main`; интегратор проверяет Actions и ставит `DONE`.

## Ветки и коммиты

Формат ветки: `<type>/<task-id>-<slug>`, например:

- `data/data-001-preprocessing`;
- `llm/llm-001-gateway-adapter`;
- `qa/qa-002-conflict-cases`;
- `rel/rel-001-gitea-release`.

Префиксы commit: `feat`, `fix`, `test`, `docs`, `research`, `chore`, `release`.
В сообщении указывается ID задачи, если смысл не очевиден.

## Конфликты зон владения

Общие файлы `TASKS.md`, `TECHNICAL_SPEC.md`, `docs/PROJECT_STATUS.md`, schema и
runtime-конфиг меняет владелец задачи с уведомлением интегратора. Если два PR
затрагивают один контракт, второй ждёт merge первого или получает отдельную
интеграционную ветку.

## Definition of Done

Задача завершена, когда результат находится в GitHub, проверен другим
участником, команды воспроизводимы, ограничения записаны, новые ошибки имеют
диагностику, а все дальнейшие действия вынесены в новые ID. Наличие файла или
ноутбука без связи с runtime и метриками не считается завершением функции.
