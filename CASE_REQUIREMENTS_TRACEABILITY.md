# GoodsAI — ТЗ кейса и трассировка требований

**Источник требований:** материалы кейса № 3 «NLP и e-commerce: ИИ для автоматического заполнения характеристик товаров» и презентация кейсодателя. Документ фиксирует требования задания; он не заменяет условия хакатона и не добавляет им новых обязательств.

## 1. Что нужно сделать по кейсу

Построить воспроизводимый пайплайн, который по текстовой товарной карточке извлекает обязательные характеристики, приводит значения к каноническому виду, выдаёт уверенность и формирует структурированный результат.

**Вход:** название, описание, атрибуты продавца.  
**Выход:** атрибут, нормализованное значение, уверенность.  
**Ограничение:** изображения в кейсе не используются.  
**Ключевой риск:** система не должна выдумывать характеристики.

## 2. Требования и как их закрывает GoodsAI

| Требование кейса | Что обязано быть в решении | Реализация GoodsAI | Артефакт-доказательство |
| --- | --- | --- | --- |
| Текстовый вход | Использовать title, description, seller attributes | Препроцессор объединяет поля, сохраняя происхождение каждого фрагмента | EDA и `preprocessing.py` |
| Обязательные поля по категории | Извлекать только релевантные атрибуты | Category schema manifest: набор полей, типы, единицы, справочники | `configs/categories.yaml` |
| Нормализация | Привести значения к каноническому виду | Словари, единицы, транслитерации, numeric parser | `normalize.py`, тесты |
| Уверенность | Сопроводить каждое значение score | Model score + валидаторы + калибровка на validation | `evaluate.py`, calibration report |
| Не выдумывать значения | LLM не должна добавлять факты от себя | В evidence-first контракте value обязан иметь span в исходном тексте; иначе `abstain` | Predictions с `evidence_text` |
| Контроль стоимости | LLM не должна вызываться на каждую карточку | Rules → local encoder → предоставленная LLM только для residual set | Cost report, LLM-call rate |
| Длинный хвост и новые категории | Не потерять редкие значения | QA-style extractor, active learning, fallback и срез cold-start | Error analysis |
| Равное качество для продавцов | Контролировать перекос | Метрики по сегментам продавцов и review для риска | Fairness slice report |
| Обратная связь | Ошибки улучшают систему | Review queue → gold labels → retrain/rule update | Annotation log |
| Честная оценка | Не ограничиваться общей accuracy | Per-attribute P/R/F1, coverage, traffic-weighted срез при наличии кликов | Metrics table |

## 3. Обязательные артефакты сдачи

| Артефакт | Минимум для приёмки | Что добавляет GoodsAI |
| --- | --- | --- |
| Код или ноутбук | Воспроизводимое решение | Один запуск pipeline и конфигурации экспериментов |
| README | Установка и запуск | Быстрый сценарий `EDA → train → predict → evaluate` |
| EDA | Поля, пропуски, распределения | Дубли, длинный хвост, конфликт источников, coverage baseline |
| Пайплайн извлечения | От текста до атрибутов | Rules, local encoder, LLM router, normalizer, validator, merger |
| Предсказания | Атрибуты для каждой карточки | Evidence span, canonical value, confidence, source, decision |
| Финальная презентация | Подход, метрики, выводы | Бизнес-ценность, стоимость и риски рядом с качеством |

## 4. Acceptance criteria для нашей команды

1. Для `auto_accept` значение имеет точное текстовое доказательство и прошло schema validation.
2. Код запускается по README на чистом окружении и фиксированном seed.
3. Сравнены минимум rules baseline и дообученный local encoder на одном test split.
4. Если задействована предоставленная LLM, показаны её incremental gain, LLM-call rate и стоимость на 1 000 карточек.
5. В финальном файле предсказаний присутствуют: `product_id`, `attribute`, `canonical_value`, `confidence`, `evidence_text`, `source`, `decision`.
6. В презентации есть отдельный слайд «риски и меры», а не только средняя метрика.

## 5. Вопросы, которые нужно закрыть после выдачи датасета

- Какие фактические названия колонок и форматы JSON/CSV?
- Дана ли категория и список обязательных полей или их надо восстановить?
- Есть ли span-разметка, либо только итоговые значение атрибутов?
- Есть ли ID продавца и клики для срезов качества/traffic prioritization?
- Какая именно нейросеть предоставляется: API, локальная модель, лимиты, цена, контекст, возможность structured output?
- Разрешены ли внешние модели и локальный GPU?

Эти ответы меняют реализацию, но не меняют базовый принцип: автоматическая запись должна быть подтверждена текстом, нормализована и проверена.

## 6. Уточнения из канала кейса

- Организаторы подтвердили, что датасет доступен для скачивания в описании кейса. Значит, EDA и rules baseline можно начинать сразу после загрузки.
- В канале участники спрашивают о перечне обязательных полей, доступе к VM, внешних LLM API и формате автоматической проверки. На приложенных сообщениях нет ответа организаторов по этим вопросам. До официального уточнения не закладываем внешние API как обязательную часть решения и не предполагаем, что перечень полей уже есть в данных.
- Полноценный пользовательский интерфейс не указан среди шести артефактов сдачи. Для продуктового чекпоинта достаточно показать продуктовый бриф, контракт входа/выхода, пайплайн, стратегию тестирования и концептуальный прототип review-сценария. Для финала нужен воспроизводимый код/ноутбук, README, EDA, пайплайн, предсказания и презентация.
