# GoodsAI — контекст проекта и продуктовый бриф

Документ задаёт общий контекст проекта для команды и следующих участников разработки. Это продуктовая гипотеза для чекпоинта, а не отчёт о готовом техническом решении. Фактические результаты, качество модели и состав датасета пока не заявляются.

## Кейс

Кейс № 3 «NLP и e-commerce: ИИ для автоматического заполнения характеристик товаров», кейсодатель — М.Видео. Нужно построить воспроизводимый пайплайн, который по тексту карточки извлекает обязательные товарные характеристики, нормализует их и сопровождает каждое предсказание оценкой уверенности.

Проблема важна для бизнеса: если характеристика не заполнена или записана несовместимым образом, товар может не попасть в фильтр. Атрибуты также используются в рекомендациях, сопоставлении одинаковых товаров от разных продавцов, сравнении, ценообразовании и аналитике ассортимента. Полная цепочка ценности — заполненные атрибуты → доступность в фильтрах → рост обнаруживаемости и CTR → возможный рост конверсии и GMV.

## Ответы на вопросы продуктового чекпоинта

### 1. Какую задачу бизнеса решаем и кто пользователь?

**Задача бизнеса:** повысить полноту и единообразие каталога маркетплейса, автоматически заполняя обязательные характеристики, которые продавцы пропустили или указали в свободном тексте. Надёжные атрибуты должны помогать покупателям находить и сравнивать товары, а командам каталога — обрабатывать больше карточек без ручного заполнения каждой характеристики.

**Основной пользователь решения:** специалист по качеству каталога или контент-оператор, который проверяет карточки с неуверенными либо спорными предсказаниями. Продавец — источник карточки и потенциальный пользователь результата, если подтверждённые атрибуты будут возвращаться ему для исправления каталога. Покупатель — конечный получатель пользы от точных фильтров и сравнения.

### 2. Какие требования и ограничения кейса учитываем?

- На входе только текстовые поля карточки: заголовок, описание и атрибуты продавца. Изображения в этом кейсе не используем.
- Нужны обязательные для категории поля, в том числе бренд, модель и ключевые характеристики. Точный список должен прийти вместе с датасетом.
- Каждое предсказание должно включать каноническое значение и уверенность модели; значения должны соответствовать формату и справочникам атрибутов маркетплейса.
- Нельзя выдумывать характеристики. Для LLM нужны ограниченная схема ответа, допустимые значения, проверка подтверждения в исходном тексте и порог уверенности.
- Низкоуверенные, конфликтующие и неподтверждённые случаи следует направлять на ручную проверку, а не автоматически записывать в каталог.
- Нужно учитывать стоимость инференса на большом каталоге: сначала дешёвые правила и словари, более дорогие модели — только для случаев, которые baseline не решил.
- Качество следует проверять отдельно по атрибутам, категориям и сегментам продавцов; средняя accuracy может скрыть провалы на редких значениях и новых категориях.
- Итоговый проект должен воспроизводимо запускаться по README и включать код, EDA, пайплайн, файл предсказаний и финальную презентацию.

### 3. Как устроен основной сценарий решения?

1. Оператор загружает или открывает карточку с заголовком, описанием и полями продавца.
2. Система определяет требуемые для категории атрибуты (по переданному датасету и таксономии).
3. Baseline на правилах и словарях извлекает очевидные значения. Если данных недостаточно или есть неоднозначность, система передаёт случай следующему доступному методу — ML-модели или LLM.
4. Значение нормализуется и сопоставляется со справочником. Для каждого поля сохраняются уверенность и текстовое подтверждение из исходной карточки.
5. Надёжные предсказания показываются как готовые к подтверждению; сомнительные — как требующие проверки. Оператор может принять, исправить или отклонить значение.
6. Проверенные исправления пополняют обратную связь для обновления словарей, правил, обучающих примеров и оценки качества.

Иллюстративный контракт результата одного поля:

```json
{
  "attribute": "memory",
  "value": "256 ГБ",
  "confidence": 0.95,
  "evidence": "256 ГБ встроенной памяти",
  "status": "ready_for_review"
}
```

Числа и пример выше демонстрационные, не результат работы модели. Концептуальный экран оператора: [prototype/index.html](prototype/index.html).

### 4. Какую ценность получают пользователь и бизнес?

- **Контент-оператор:** меньше ручного поиска характеристик в описаниях; в первую очередь проверяет неоднозначные случаи и видит, на какой фрагмент текста опирается предсказание.
- **Продавец:** карточки полнее, меньше повторного ввода и риска, что товар не будет найден из-за пустого фильтруемого атрибута.
- **Покупатель:** больше релевантных товаров в фильтрах и более корректное сравнение предложений.
- **Бизнес маркетплейса:** качественнее каталог и сигналы для поиска, рекомендаций и аналитики; потенциальный рост CTR, конверсии и GMV должен быть проверен экспериментом, а не предполагается доказанным заранее.

### 5. По каким метрикам поймём, что решение работает?

**Качество атрибутов:** precision, recall и F1 для каждого обязательного атрибута на размеченном эталоне. Дополнительно — macro-F1 по атрибутам, чтобы редкие поля не терялись за частыми.

**Полнота и доверие:** coverage (доля карточек, где атрибут заполнен); доля автоматически принимаемых предсказаний при заданном пороге; точность среди авто-принятых значений; доля ошибок/исправлений при ручной проверке.

**Справедливость покрытия:** качество и coverage отдельно по категориям, редким значениям и сегментам продавцов, включая новые категории и длинный хвост.

**Экономика и продуктовый эффект:** стоимость и задержка обработки карточки; доля карточек, проходящих без ручной проверки; после интеграции — CTR фильтров, конверсия и GMV в контролируемом эксперименте.

Численные целевые значения нужно согласовать после изучения датасета, baseline и цены ручной проверки. Эталон для проверки должен быть размечен людьми и содержать примеры по категориям, включая редкие значения.

## План технической проверки гипотезы

1. Изучить схему, пропуски, распределения и разметку входного датасета; зафиксировать обязательные атрибуты и правила нормализации.
2. Собрать baseline на регулярных выражениях и словарях; измерить per-attribute precision/recall/F1 и coverage.
3. Добавить модельный метод для свободных формулировок и длинного хвоста; сравнить качество, стоимость и задержку с baseline.
4. Проверить гибридную маршрутизацию и пороги уверенности на отложенном gold-сете, включая редкие категории.
5. Подготовить воспроизводимый запуск и файл предсказаний для каждой карточки; описать ошибки, ограничения и дальнейшие шаги.

## Что пока неизвестно

- Датасет и фактические названия/форматы полей.
- Перечень обязательных атрибутов и справочников для каждой категории.
- Объём и качество обучающей/валидационной разметки.
- Какие модели, вычислительные ресурсы и внешние API доступны команде.
- Базовые значения продуктовых метрик и целевые пороги качества/стоимости.

До получения этих данных не следует представлять архитектурные гипотезы, демонстрационный пример или метрики как реализованные результаты.
