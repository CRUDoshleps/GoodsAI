# GoodsAI — продуктовый чекпоинт: сценарий презентации

**Формат:** PDF, 10 слайдов, до 5–7 минут выступления.  
**Цель:** получить максимум по критериям «Соответствие задаче кейса» и «Продуктовая ценность».  
**Правило:** слайды 2–7 отвечают на пять обязательных вопросов в явном виде. На каждом таком слайде указывается номер вопроса из брифа.

## Главная мысль питча

> **GoodsAI возвращает товары в поиск и фильтры: заполняет только подтверждённые текстом характеристики и тратит дорогую обработку лишь на сложные, важные для спроса карточки.**

Мы не обещаем автономно «угадать» каждую характеристику. Система принимает решение из трёх исходов: `auto_accept`, `review`, `abstain`. Поэтому неполное описание не превращается в ложный факт в каталоге.

### На слайде

**GoodsAI**

Подзаголовок: *Evidence-first гибрид: правила → локальная модель → LLM только для сложного остатка.*

«Пустая характеристика исключает товар из фильтров. GoodsAI находит значение в тексте, приводит его к формату каталога и автоматически записывает только тогда, когда может показать текстовое доказательство».

## Слайд 2. **1. Проблема бизнеса и пользователь**

### На слайде

```text
Неполная карточка
        ↓
Товар отсутствует в фильтре и поисковой выдаче
        ↓
Покупатель не находит товар
        ↓
Потеря CTR / конверсии / GMV
```

| Пользователь | Проблема сегодня | Результат GoodsAI |
| --- | --- | --- |
| Контент-оператор | Вручную ищет характеристики и проверяет их | Получает значение, источник и готовое решение |
| Продавец | Карточка не проходит по обязательным полям | Видит, какое поле пустое или конфликтно |
| Покупатель | Не находит релевантный товар через фильтры | Видит больше подходящих товаров |
| Каталог / поиск | Неполные и несопоставимые признаки | Получает нормализованные атрибуты |

### Речь — 35 секунд

«Главный пользователь — оператор качества каталога. Для покупателя результат заметен в поиске и фильтрах, для продавца — в более полной карточке. Бизнес-цель — не извлечь текст ради текста, а повысить *валидное* покрытие атрибутов, от которого зависят поиск, рекомендации и конверсия».

## Слайд 3. **2. Требования кейса, которые закрывает решение**

### На слайде

| Требование платформы | Решение GoodsAI |
| --- | --- |
| Только title, description и поля продавца | Не используем фото и OCR |
| Не выдумывать характеристики | У каждого `auto_accept` есть `evidence span` в тексте |
| Канонический формат | Нормализатор единиц, цветов, транслитераций и словари категорий |
| Уверенность | Калиброванный score + результат проверки |
| Масштаб и стоимость | Каскад; LLM получает только residual set |
| Редкие категории и продавцы | Метрики по атрибутам, категориям и продавцам; review для риска |
| Улучшение со временем | Исправления оператора становятся gold-разметкой |

Нижняя плашка: **Если доказательства в тексте нет — `abstain`, а не догадка.**

### Речь — 35 секунд

«Основной риск кейса — ложное значение. Поэтому уверенность сама по себе недостаточна: запись в каталог проходит только после проверки происхождения, формата и отсутствия конфликта источников».

## Слайд 4. **3. Основной сценарий: Demand-Aware Evidence Cascade**

### На слайде

```text
query_clicks* → очередь по ожидаемой пользе
                         │
title + description + seller fields
                         ↓
1. Rules + dictionaries + numeric parser
                         ↓  сложный / нераспознанный случай
2. Локальный encoder: кандидат-спан + confidence
                         ↓  низкая уверенность / конфликт / новая категория
3. Fast model шлюза, затем strong model только для редкого остатка: JSON-кандидат по строгой схеме
                         ↓
4. Normalizer + evidence verifier + schema validator
                         ↓
          auto_accept / review / abstain
                         ↓
       правка оператора → active learning
```

`*` Очередь по спросу включается только если EDA подтвердит связи между запросами, кликами и SKU.

Сбоку покажите формулу приоритета:

`priority = query_demand × missing_rate × expected_precision`

### Речь — 50 секунд

«Это не три модели, голосующие друг за друга. Это каскад стоимости и риска. Правила мгновенно закрывают очевидные форматы вроде `256GB`. Локальный encoder работает со свободным текстом. LLM видит только сложный остаток. После любого источника стоит независимый verifier: он подтверждает, что нормализованное значение действительно присутствует в тексте и подходит схеме категории».

### Что реализуем технически

| Слой | Реалистичная реализация для хакатона |
| --- | --- |
| Подготовка и EDA | Python 3.11, Polars или Pandas, DuckDB, Parquet, Jupyter |
| Схема категорий | YAML: обязательные поля, единицы, диапазоны, словари, пороги |
| Rules / normalizer | `re`, `pydantic`, `rapidfuzz`; отдельные парсеры чисел и единиц |
| Локальная модель | Hugging Face `transformers` + PyTorch; дообучаемый русскоязычный BERT-encoder для token classification или извлечения span |
| Проверка | Exact/normalized span match, типы и диапазоны, conflict detector |
| Model gateway | OpenAI SDK на VM; fast model для массового остатка, `openai/gpt-oss-120b` для редких конфликтов; JSON schema, лимит токенов, cache |
| Review demo | Streamlit или статический HTML-прототип |
| Воспроизводимость | `uv`/`pip`, `pytest`, фиксированный seed, конфигурации экспериментов |

## Слайд 5. **3. Прототип: решение оператора за один экран**

### На слайде

Покажите review-экран с одной карточкой и тремя кейсами:

| Атрибут | Результат | Доказательство | Решение |
| --- | --- | --- | --- |
| Объём памяти | `256 ГБ`, 0.98 | «…память **256GB**…» | `auto_accept` |
| Цвет | «чёрный» / «графитовый» | title и description противоречат | `review` |
| Ёмкость батареи | — | значения нет в тексте | `abstain` |

Кнопки: **Принять · Исправить · Отклонить**. Под каждым значением: источник, confidence, версия правила/модели.

### Речь — 35 секунд

«Оператор не ищет ответ заново. Он проверяет предложенный факт и его доказательство. Конфликт мы не замалчиваем, а отправляем на review. Отсутствующее значение не выдумываем».

## Слайд 6. **4. Ценность для пользователя и бизнеса**

### На слайде

| Кому | Ценность | Как подтверждаем |
| --- | --- | --- |
| Оператору | Меньше ручного поиска и понятная проверка | Время review на карточку, доля auto-accept |
| Покупателю | Больше релевантных товаров в фильтрах | Traffic-weighted valid coverage |
| Продавцу | Понятные пробелы и конфликты в данных | Seller quality score, доля исправлений |
| М.Видео | Полнее каталог без отправки всех SKU в LLM | Precision auto-accept, LLM-call rate, cost / 1 000 SKU |

**Продуктовая фича:** *seller quality score* — доля пустых обязательных полей, конфликтов и операторских исправлений по продавцу. Он помогает устранять источник плохих данных, а не только исправлять последствия.

### Речь — 35 секунд

«GoodsAI создаёт два контура ценности: сейчас возвращает товары в поиск, а затем показывает бизнесу, где именно рождаются плохие данные. Поэтому это инструмент качества каталога, а не разовая модель извлечения».

## Слайд 7. **5. Метрики и стоимость**

### На слайде

| Группа | Метрика | Почему она нужна |
| --- | --- | --- |
| Качество | Precision / Recall / F1 **по каждому атрибуту** | Средняя accuracy скрывает ошибки на хвосте |
| Безопасность | Precision `auto_accept`, evidence-pass rate, conflict rate | В каталог не должны попадать ложные факты |
| Полнота | Valid coverage | Считаем только валидно заполненные поля |
| Польза | Traffic-weighted valid coverage | Важнее заполнить то, что ищут и фильтруют |
| Операции | Review rate, время review, abstain rate | Измеряем нагрузку оператора |
| Экономика | LLM calls / 1 000 SKU и cost / 1 000 SKU | Контролируем масштабирование |
| Равенство качества | F1 и coverage по категории и продавцу | Видим просадки на long tail |

Формула стоимости для отчёта:

`cost_1000 = local_compute_1000 + llm_calls_1000 × cost_per_llm_call + review_minutes_1000 × operator_rate`

### Речь — 40 секунд

«Не обещаем заранее рублёвую экономию или рост GMV: это нужно посчитать на данных и тарифе предоставленной модели. Но с первого запуска мы показываем измеримую долю LLM-вызовов, стоимость на тысячу SKU и качество автоматически принятых фактов».

## Слайд 8. Риски и политика решений

### На слайде

| Риск | Защита | Результат |
| --- | --- | --- |
| Галлюцинация LLM | JSON schema + evidence span + verifier | Нет доказательства → `abstain` |
| Title и description противоречат | Source-aware conflict detector | `review` |
| `256GB`, `0.25 TB`, `256 Гб` | Unit normalizer + canonical dictionaries | `256 ГБ` |
| Редкие значения и новые категории | Fast/strong модели шлюза, active learning, отдельный cold-start срез | Контролируем деградацию |
| Рост стоимости | Rules → encoder → fast model → strong model, cache, лимит бюджета | Измеряемый cost cap |
| Некачественный продавец | Seller quality score и сегментные метрики | Видим источник ошибки |

Политика принятия:

```text
auto_accept = доказательство + валидная схема + нет конфликта + score ≥ порога атрибута
review      = доказательство есть, но есть конфликт или score в серой зоне
abstain     = доказательства нет или проверка не пройдена
```

### Речь — 35 секунд

«Главное качество здесь — не максимальное заполнение любой ценой. Мы управляем риском: сомнительную информацию не превращаем в структурированный факт».

## Что должно быть готово к демонстрации

1. **Работающее мини-демо на 10–20 карточках:** не только happy path, но и конфликт, транслитерация, разные единицы, редкий бренд, отсутствие значения.
2. **Прототип review-экрана:** исходный текст, evidence span, confidence, решение, действие оператора.
3. **Схема категорий в YAML:** поле, тип, единицы, диапазоны, словарь, порог.
4. **Скрипт или ноутбук EDA:** показать реальные поля и возможности `query_clicks` без вымышленных связей.
5. **Один экран метрик:** coverage, precision `auto_accept`, review/abstain, LLM-call rate, cost / 1 000 SKU.

## Чего не говорить на защите

- Не называть произвольную сумму экономии, рост CTR или GMV до эксперимента.
- Не использовать цифры из научных статей как результат своей модели.
- Не обещать, что LLM заполняет характеристику, которой нет в тексте.
- Не заявлять, что traffic prioritization уже работает, пока EDA не подтвердит связи в `query_clicks`.
- Не описывать полноценный кабинет продавца как готовую часть MVP: показать его как следующий продуктовый контур.

## Текст для поля «Описание решения» на платформе

> GoodsAI — гибридный сервис автоматического заполнения характеристик товаров. Он извлекает обязательные атрибуты из title, description и полей продавца, нормализует значения и возвращает confidence вместе с доказательством в исходном тексте. Каскад «правила и словари → локальный encoder → LLM только для сложного остатка» снижает стоимость обработки каталога. Независимый validator проверяет наличие evidence span, допустимый формат, единицы и конфликты источников; карточка получает `auto_accept`, `review` или `abstain`. Исправления оператора образуют петлю active learning. В метриках измеряем F1 по атрибутам, valid coverage, precision auto-accept, review rate, LLM calls и cost на 1 000 SKU; при подтверждении связей в `query_clicks` добавляем traffic-weighted quality.
