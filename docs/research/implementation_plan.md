## Что согласовать первым

Рекомендуемый эксперимент E1: text-only rules baseline для смартфонов `761` и
электрических чайников `482`, нормализация, verifier, JSONL и ручная оценка.
Обучение локального encoder и многоуровневый LLM-router отложены.
Сравнение с одним ML/LLM-подходом запланировано после E1, с отдельным разрешением
на доступ к моделям и передачу данных. Отсутствие такого сравнения к 23 октября
будет открытым пунктом задания, а не поводом объявить rules полной реализацией кейса.

Основание: [EDA](dataset_findings.md), [контракт](architecture_and_contract.md),
[оценивание](evaluation.md). До реализации подтвердить предлагаемую схему
атрибутов и допустимость ограниченного охвата на первом checkpoint.

## Распределение между четырьмя участниками

| Роль | Основная зона | Результат для команды |
| --- | --- | --- |
| Участник 1 — данные/интеграция | T1, T2, CLI и manifests | Воспроизводимый ограниченный вход, стабильные ID/split, запуск |
| Участник 2 — смартфоны | Правила RAM/ROM/диагонали/цвета, tests | Кандидаты по схеме, отсутствие путаницы с картой памяти/камерой/частотой |
| Участник 3 — чайники/нормализация | Правила объёма/мощности/цвета, Decimal, verifier | Единицы, span, конфликтные случаи и единый формат |
| Участник 4 — оценка/QA | Gold, evaluator, результаты, сравнительный эксперимент | Независимые метрики, error analysis, финальные материалы |

Все участвуют в ручной разметке; автор правила не должен единолично утверждать
его test-примеры. Участник 4 координирует независимую проверку, но не размечает
всё в одиночку. Общие contracts/schema принадлежат интегратору; изменения через
PR и согласование. Имена и конкретные ветки назначает команда. Codex помогает
реализовывать отдельные задачи; научные выводы требуют реальных измерений.

## Что должен создать следующий Codex

Минимальная рекомендуемая структура, без пустых заготовок:

```text
pyproject.toml                     версии Python, CLI и минимальные зависимости
configs/baseline.json              две категории, requested fields, режимы
src/goodsai/contracts.py           вход/выход и валидация схемы
src/goodsai/data.py                пакетное чтение, join, provenance, no-leakage
src/goodsai/rules.py               правила с category dispatch; пока один модуль
src/goodsai/normalize.py           числа, единицы и согласованные алиасы
src/goodsai/verify.py              evidence, schema, конфликты
src/goodsai/evaluate.py            подсчёт метрик по согласованному gold
src/goodsai/cli.py                 prepare / predict / evaluate
tests/test_data.py
tests/test_rules_and_normalization.py
tests/test_contract_and_evaluation.py
README.md                         команды запуска после согласования правки
```

Это проект структуры для реализации, а не требование создавать все файлы заранее.
Не создавать service/controller/repository: задача явно Python/NLP CLI без веб-API.
Не добавлять torch/transformers, Jupyter, pandas и сервер БД без конкретной нужды.
Зависимости baseline зафиксировать отдельно от исследовательского инструментария.
Малые словари правил — код/конфигурация с происхождением; массивы реальных
каталожных значений и весь gold — локально в `data/`, не в Git.

Предлагаемый интерфейс будущего CLI (сейчас этих команд **нет**):

```powershell
python -m goodsai.cli prepare --config configs/baseline.json --output data/processed/pilot.jsonl
python -m goodsai.cli predict --input data/processed/pilot.jsonl --output outputs/baseline/predictions.jsonl
python -m goodsai.cli evaluate --predictions outputs/baseline/predictions.jsonl --gold data/gold/validation.jsonl --output outputs/baseline/metrics.json
```

## Проверки готовности E1

1. Дубликат SKU, неизвестная категория, отсутствующее описание, `param` dict/list,
   повторное имя параметра и расхождение title обрабатываются явно.
2. На синтетических тестах: `6/128GB`, `6+128GB`, `1,7 л`, `1700 мл`, `2 400 Вт`,
   NBSP, диапазоны, HTML-теги, отсутствие значения, противоречащие источники,
   RAM против ROM/карты памяти, standby power против основного нагревателя.
3. Evidence указывает на исходное поле и точные offsets; текст после очистки
   не выдаётся за исходный. Число из URL/HTML-атрибута не становится характеристикой.
4. Gold отсутствует → evaluator сообщает об отсутствии оценки; при известном
   синтетическом gold правильно считает wrong value как FP+FN, abstain как FN
   только для `present`, не включает ambiguous в основную метрику.
5. Закрытые targets/алиасы не попадают во вход extractor; split не пересекается
   по группам. Не использовать SKU lookup готового атрибута как извлечение.
6. Выход содержит ровно столько SKU, сколько во входе; JSONL валиден, requested
   attributes покрыты ответом/отказом; ошибки учтены, метрики имеют denominators.
7. Второй запуск с теми же данными/версией даёт те же значения и решения
   (служебный run_id и время сравнивать отдельно). Измерены elapsed time и RSS.
8. Исходные SHA неизменны, данные/gold/предсказания игнорируются Git, сеть
   для baseline не нужна. Структурные invariants обязательны; порог F1 пока не задан.

## Первый промпт Codex на реализацию

Использовать **после согласования этого плана**, в отдельной задаче:

```text
Реализуй минимальный Python 3.12 text-only baseline GoodsAI по документам
docs/research/dataset_findings.md, architecture_and_contract.md, evaluation.md
и implementation_plan.md. Сначала проверь Git и текущие файлы; сохрани чужую работу.
Работай в согласованной feature-ветке, не в main. Коммиты, push и VM не выполняй.

Scope: смартфоны category_id=761 и электрические чайники category_id=482.
Сначала T0–T8: пакетный адаптер реальных файлов, правила, нормализация, verifier,
JSONL и evaluator. Не обучай модели, не используй LLM/API и не создавай UI.
Не загружай весь pickle в память. Для доверенного каталога используй проверенную
локальную проекцию/подготовительный reader с проверкой SHA и покрытия категорий.
Не меняй data/raw. Все данные, gold и результаты остаются вне Git.

Вход extractor: SKU, category, исходный name каталога и joined description.
Vendor/model/target params оставь отдельно как weak reference; не передавай
готовые ответы extractor и не используй SKU lookup. Сохраняй оба title для аудита.
Ожидаемый пилот: 10 324 SKU, 4 244 с описанием и 6 080 title-only на текущем снимке.

Первый набор: brand, RAM/ROM, диагональ, базовые цвета для смартфонов;
brand, объём, мощность, базовые цвета для чайников. Requested model/battery
без надёжного правила должны иметь явный abstain, а не выдуманное значение.
Согласованные единицы/алиасы — в версии схемы. Каждое непустое значение обязано
иметь проверяемый raw evidence span. Confidence правил пометь heuristic.

Создай минимальные модули и тесты из плана, CLI prepare/predict/evaluate,
фиксированные зависимости и инструкции запуска. Используй синтетические fixtures
для unit tests. Реальный gold не придумывай: подготовь разметочное задание и split
manifest, при отсутствии ручной разметки выводи качество N/A с объяснением.
Сделай smoke-run, полный пилот, проверь счётчики, invariants, воспроизводимость
и память. Покажи diff, реальные результаты и оставшиеся ограничения.
После этого остановись для проверки командой.
```
