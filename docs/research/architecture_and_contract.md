# Рекомендация по архитектуре и предварительный контракт

Дата: 17 октября 2026 года. Предложение для согласования, не реализованный pipeline.
Основание — [фактический EDA](dataset_findings.md), а не обещанные метрики презентации.

## Решение для ближайшего этапа

К 19 октября: пакетный Python CLI, правила и небольшие проверенные словари,
нормализация, проверка свидетельства и JSONL. Первые категории — **смартфоны 761**
и **электрические чайники 482**. Обучение локального encoder отложить.
После оценки правил — один ограниченный эксперимент с разрешённым LLM либо
другим ML-методом, как требует кейс; запуск согласовать отдельно.

Причины выбора категорий:

| Категория | Каталог | С описанием | С наблюдениями в query_clicks | Решение |
| --- | ---: | ---: | ---: | --- |
| Смартфоны 761 | 7 988 | 3 056 | 7 677 | Первый пилот: память, экран, цвет, бренд |
| Чайники 482 | 2 336 | 1 188 | 1 963 | Второй пилот: объём и мощность, иная структура атрибутов |
| Ноутбуки 987 | 3 580 | 1 327 | 3 301 | Следующее расширение; много неоднозначных чисел, RAM/SSD/VRAM/ядра |
| Телевизоры 1682 | 3 175 | 1 341 | 3 067 | Резервная категория; дисплей/цвет/мощности разных компонентов |
| Мониторы 1263 | 1 880 | 546 | 1 697 | Резерв; меньше описаний |

Частоты наблюдений не являются доказанным CTR. Две первые категории дают
4 244 карточки с описанием и 6 080 без описания: всего 10 324. На первом
чекпоинте запускать обе подвыборки, качество и coverage показывать отдельно.
Это ограниченный пилот, не решение для всех 3 599 используемых категорий.

## Сравнение вариантов

Оценки времени ниже — плановые оценки инженерной работы, не измерения качества.

| Подход | Преимущество для этих данных | Риски и стоимость | Срок/VM | Решение |
| --- | --- | --- | --- | --- |
| Rules + dictionaries | Явные единицы, память в названиях, бренд; точный span; легко анализировать ошибки | Низкий recall на нестандартных названиях; конфликт цветов и числовых контекстов | Около 1–2 дней на две категории вместе с оценкой; пакетное CPU-исполнение правдоподобно, замер обязателен | Первый baseline |
| LLM + схема | Может разобрать свободный текст и неизвестные формулировки без обучения | JSON-схема не гарантирует фактическую истинность; неизвестны доступ, лимиты и цена; запрещена текущая передача данных API | Около дня на небольшой эксперимент после доступа и gold-set; VM может быть клиентом, ресурсы сервера неизвестны | Контрольное сравнение позже, только с разрешением |
| Гибрид rules → LLM для остатка | Позволяет измерить добавочное покрытие там, где правила отказались | Router и cache добавляют сложность; неверное уверенное правило не попадёт в fallback; нужно оценивать общую систему | Дополнительно 1–2 дня после E1 и LLM-проверки | Целевая опция, если измерен выигрыш |
| Локальная NLP-модель | Возможный будущий рост покрытия и независимость от API | Нет проверенной span-разметки; weak labels шумные; обучение, калибровка и перенос на CPU отнимут время | Для обучения GPU не подтверждён; 2 CPU / 4 ГБ не планировать как среду fine-tuning encoder; CPU-инференс конкретной модели потребует замера | Не включать в критический путь к 19 октября |

Пять уровней из презентации сейчас преждевременны. Verifier и нормализация нужны
с первой версии; локальная модель не является обязательной промежуточной ступенью
перед LLM. Простая локальная модель может стать последующим экспериментом, если
error analysis выделит конкретный тип ошибок, появится размеченная выборка и
ресурс для проверки. Не обещать превосходство ни одного метода до сравнения.

## Минимальный путь данных

```text
catalog SKU + category + name  ← join по SKU →  description
                     ↓
             адаптер и флаги качества
                     ↓
        схема категории → правила/словарные кандидаты
                     ↓
       нормализация → проверка контекста/span/конфликтов
                     ↓
         результат по каждому SKU + явные отказы
                     ↓
          JSONL + отдельный отчёт оценки
```

Клики не являются входом extractor. Структурированные ответы каталога хранятся
отдельно от text-only входа. Для официально разрешённого режима с seller fields
нужен отдельный адаптер с защитой от утечки, описанной в `evaluation.md`.

Не читать все исходные файлы в память. Один локальный подготовительный проход
должен сформировать безопасную табличную проекцию нужных категорий. Рабочий
baseline затем читает её пакетами, не десериализуя pickle при каждом запуске.
Исследовательский `catalog_skus.parquet` уже есть локально, но его `params_json`
сохранены только для пяти исследованных категорий; это не полный универсальный
экспорт. Боевой адаптер следующего этапа должен явно проверить покрытие и входной
manifest, либо выполнить отдельную подготовку. Никакой загрузки произвольных
pickle от пользователя через CLI baseline.

## Атрибуты первой версии

Перечень ниже — рабочая схема E1. В задании прямо перечислены поля смартфона:
бренд, модель, объём памяти, диагональ, батарея и цвет; все они представлены
ниже, RAM выделена нами дополнительно. Чайник — наш пилотный выбор, отдельного
официального перечня для него в переданном тексте нет. Полная нормативная схема
и справочники по категориям ещё не подтверждены. Подробности и требования
к сдаче — в [актуальном разборе задания](../REQUIREMENTS_AND_DELIVERY.md).

| Поле | Категория | Weak reference в каталоге | Метод первой версии |
| --- | --- | --- | --- |
| `brand` | обе | `vendor` | Проверенный словарь development + границы слова/длиннейшее совпадение |
| `model` | обе | `model`, `Модель_search` | Только уверенно выделяемый span модели в названии; неоднозначное — abstain; улучшение после первого checkpoint |
| `storage_gb` | смартфон | `Встроенная память (ROM)_search` | Контекст встроенной памяти; разбор проверенных `6/128GB`, `6+128GB` |
| `ram_gb` | смартфон | `Оперативная память (RAM)_search` | Контекст ОЗУ/RAM; отличать от ROM и поддерживаемой карты памяти |
| `screen_inches` | смартфон | `Диагональ_search` + `@unit` | Число и дюйм/диагональ; не частота обновления и не размер корпуса |
| `battery_mah` | смартфон | `Емкость аккумулятора_search` | Контекст аккумулятора и мАч; следующий приоритет после памяти/экрана |
| `color` | обе | `Цвет_search`, иногда `Цвет производителя_search` | Небольшой согласованный словарь; конфликт оттенков — review |
| `capacity_l` | чайник | `Максимальный объем_search` | Число + л/мл в контексте основного объёма; не объём заварника |
| `power_w` | чайник | `Потребляемая мощность_search` | Вт/кВт в контексте нагревателя; не standby-мощность |

Память и единицы: заранее зафиксировать соглашение GB/TB, не молча смешивать
десятичные и двоичные единицы; на первом пилоте поддержать явные GB/ГБ, а
неоднозначный TB оставить отказом до решения схемы. `Гб` в товарном тексте
может означать гигабайт при нестрогой записи, но это доменное правило, которое
нужно отдельно покрыть тестом. Не интерпретировать число рядом с «картой памяти»
как встроенную память. Числа разбирать через Decimal; запятую, пробелы и NBSP
нормализовать с сохранением исходного span.

Закрытые цветовые классы задаёт команда после разметки: «темно-синий» не заменять
на «синий» без явного решения схемы. Материал «нержавеющая сталь» нельзя молча
превращать в цвет. Не выводить характеристики по знанию модели телефона:
отсутствующая в тексте характеристика должна остаться `abstain`.

## Входной контракт v0.1

UTF-8 JSONL, один объект на товар; следующая запись **синтетическая**:

```json
{
  "schema_version": "0.1",
  "sku_id": "demo-001",
  "category_id": "482",
  "title": "Электрочайник Example K1 белый",
  "description": "Объём 1,7 л. Мощность 2200 Вт.",
  "seller_attributes": [],
  "source_flags": []
}
```

- `sku_id` — непустая строка; адаптер сохраняет исходный ID, не invent surrogate.
- `category_id` — строка ID из каталога либо null с `unknown_category`.
- `title` из `skus.name`, `description` из `sku_desc.description` по SKU.
  Отсутствующее описание — null + `missing_description`, не ошибка загрузки.
- Оригинальный `sku_desc.title` сохраняется в локальной provenance-таблице;
  при расхождении ставится `title_mismatch`. Его не подмешивать незаметно.
- `seller_attributes` — список `{name, value, unit}`, сохраняющий дубли. В E1
  список пуст. В разрешённом enrichment-режиме все скрытые targets и алиасы
  удаляются до вызова extractor.
- `vendor`, `model`, gold values, split и click statistics не входят в объект
  text-only extractor. Они существуют в отдельных локальных таблицах оценки.
- Нет категории/неподдерживаемая категория — отдельный статус результата,
  без попытки автоматически угадать её по query_text.

Предобработка не должна уничтожать координаты: первая версия хранит исходные
title/description и ищет кандидаты по текстовым сегментам HTML с отображением
на исходные позиции. Не вытаскивать значения из href/src/script/style. Если
очистка меняет длину текста, нужен offset map; иначе нельзя заявлять raw-span.

## Выходной контракт v0.1

Один объект на каждый входной SKU, включая ошибки/неподдержанные категории.
Это наш предварительный JSONL-формат; формат загрузки организаторам ещё неизвестен.
Следующий пример **синтетический**, confidence демонстрационный, не замер:

```json
{
  "schema_version": "0.1",
  "run_id": "rules-v0-demo",
  "sku_id": "demo-001",
  "category_id": "482",
  "status": "processed",
  "attributes": [
    {
      "attribute": "capacity_l",
      "value": "1.7",
      "unit": "L",
      "confidence": 0.8,
      "confidence_kind": "heuristic",
      "decision": "review",
      "method": "rule",
      "rule_id": "kettle.capacity.explicit.v1",
      "evidence": {"field": "description", "start": 6, "end": 11, "text": "1,7 л"},
      "reason_codes": []
    }
  ]
}
```

Для реального результата перечислить **каждый запрошенный атрибут** категории,
включая отказ. При отказе `value/unit/confidence/evidence = null`, `decision=abstain`,
`reason_codes` содержит `not_in_text`, `conflicting_evidence`, `unsupported_format`
или другую версионированную причину. `confidence_kind=heuristic` у некалиброванных
правил; это не вероятность истинности. `auto_accept` разрешать только после
выбора порога на validation. До этого результаты — кандидаты `review`.

Числовые канонические значения — десятичные строки с точкой без разделителей
тысяч, unit — код из схемы (`GB`, `inch`, `mAh`, `L`, `W`); текстовые значения
также строки, unit=null. Это исключает неоднозначность float при сериализации.
Индексы evidence: Unicode code points, zero-based, end-exclusive относительно
исходного поля, **до** нормализации. В примере `description[6:11] == "1,7 л"`.

Инварианты: уникальный SKU на входе и выходе; ровно один ответ на запрошенный
атрибут; span совпадает с исходным текстом; значение согласуется со смыслом span,
типом, единицей и схемой; конфликт не скрывается выбором первого совпадения.
Статусы товара: `processed`, `unsupported_category`, `invalid_input`, `error`.
`processed` допускает все атрибуты в abstain — это не успех извлечения.

Manifest запуска сохраняет SHA-256 источников, commit кода, схему, словари,
конфигурацию, seed, входные/выходные счётчики и версии зависимостей. Предсказания,
gold и проекции данных остаются в исключённых `outputs/` и `data/`.

## Решения, которые ещё нельзя принять по имеющимся файлам

1. Официальный список required attributes и канонические справочники.
2. Есть ли отдельная ручная разметка/скрытый test, не попавшие в эти три файла.
3. Единица строки query_clicks, период логов и различие subject/seo ID.
4. Формат и полный охват финального файла предсказаний.
5. Разрешение на обработку карточек шлюзом, имена моделей, лимиты и цена.

Без этих ответов можно реализовать и честно оценить ограниченный rules baseline.
Полную готовность к автоматической проверке хакатона заявлять нельзя.
