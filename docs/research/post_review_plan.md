входы/выходы/ограничения; pipeline расширяется одним проверяемым модельным
этапом, а решения принимаются по явной политике. Качество сравниваем с
неизменным rules baseline. Баллы следующего LLM-review заранее не обещаем.

1. **P0, ближайший пакет:** воспроизводимый демонстрационный комплект,
   индекс реальных метрик и артефактов, актуальный статус ВМ; устранение

3. **Следом:** расширить reviewed reference; подготовить и выполнить один

4. **P1:** расширить проверенную разметку/категории, оценить пороги и
   подготовить финальную техническую презентацию и комплект сдачи.
5. **19 октября вечером**, после получения обещанной спецификации:

## Модельный этап: варианты и выбранное направление

- **Правила + ограниченный LLM fallback через шлюз организаторов:**
  рекомендуемый первый модельный опыт для неразобранного model. Пользователь
  18 октября подтвердил выданный доступ; на скриншоте есть endpoint, модели,
  тарифы и 100 ₽/день. На ВМ уже заданы OPENAI_BASE_URL/OPENAI_API_KEY.
  Проверить совместимость выбранного режима, учёт tokens/бюджета, отказы и
  качество. Снимок панели не доказывает успешный API-вызов. Произвольные
  сторонние API не входят в этот контур; реальные gold/targets не передавать.
- **Правила + локальная instruction LLM:** резерв, если выданный шлюз
  непригоден; потребуется отдельная проверка ресурсов/весов. Загрузка модели
  на командную ВМ не нужна для основного рекомендованного пути.
- **Правила + локальная ML/NER-модель:** данные остаются локально, но нужны
  подходящая модель/лицензия, ресурсы и проверенная разметка; текущего reference
  недостаточно, чтобы обещать полноценное обучение и обобщение.
- **Только развитие rules:** быстрый адресный выигрыш, особенно model, но
  само по себе не закрывает замечание о модельном этапе и требование попробовать
  ML или LLM. Это ближайший инкремент, а не конечный план.

Первое действие R7 после разрешения запуска — синтетическая проверка выданного
шлюза с переменными окружения ВМ, затем ограниченный dev-эксперимент.
Предлагаемый расход первой итерации — до 10 ₽ в пределах командных 100 ₽/день;
полные условия и модели — в плане model. Ожидание большого
gold не блокирует проектирование/синтетические тесты, но без ручной оценки нельзя
утверждать прирост качества. Никаких внешних вызовов этот план сам не разрешает.
Для новых категорий одного наличия LLM недостаточно: нужна схема и отдельная оценка.

Отдельно согласовать следующий scope после E1: категории и допустимые текстовые
поля продавца. Текущий запрет непустых seller_attributes снимать только в рамках
версии контракта с явной границей между входным текстом и готовыми target params;
расширение проверять отдельными срезами, не смешивая его эффект с заменой метода.

## Принятие значений и честная оценка

Не превращать текущие 0,75/0,8/0,85 в вероятности. Перенос этих констант в JSON
не является калибровкой. Сначала задать безопасную конфигурируемую policy с
auto_accept=false, затем собрать проверенные примеры, выбрать целевую precision
и пороги по атрибутам на development/calibration. Проверить качество принятого
подмножества и его coverage на отдельной выборке с достаточным support;
для неподтверждённых срезов оставить review. Изменение decision требует
согласования и обновления контрактных тестов/evaluator/README.

reviewed-v2 сохранить как историческую диагностику. Его validation уже обсуждался
при разработке политики и не становится новым независимым holdout. Правила
улучшать по development; для итогового сравнения зарезервировать отдельные группы
и независимую проверку. Сравнивать rules-only и hybrid на одних входах:
per-attribute/category P/R/F1, FP/FN, abstentions, candidate/accepted coverage,
доля model-вызовов, стоимость и p50/p95. Никаких заявлений об улучшении до замера.

## Данные и комплект сдачи

Raw, реальная разметка и predictions остаются вне Git согласно AGENTS.md.
Ближайшее безопасное решение для видимости в репозитории: синтетические входы,
пример полного ответа в документации, агрегированные таблицы и исполняемые
команды генерации outputs. Готовые реальные predictions + manifest передавать
в разрешённом архиве/канале организаторов; место и права доступа уточнить.
Если организаторам нужен именно файл в Git, отдельно согласовать изменение
политики публикации. Не добавлять реальные данные ради балла LLM-review.

Существующая продуктовая презентация не заменяет финальную техническую:
последняя должна отражать реально исполняемый pipeline, сравнение методов,
число и происхождение меток, стоимость/задержку, ограничения и SHA релиза.
