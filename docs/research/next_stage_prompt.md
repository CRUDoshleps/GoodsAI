# GoodsAI — промпт следующего этапа: проверенный reference и первая оценка

Подготовлено 17 октября 2026 года. Это план следующего запуска; его действия
не выполнялись при создании документа.

Этап выполнен отдельным запуском 17 октября: [отчёт первой оценки](first_baseline_evaluation.md).
Заморожен reviewed-v1 (9 development, 8 validation), исходные predictions и
runtime сохранены. Этот промпт остаётся исторической инструкцией; повторный
запуск не должен перезаписывать reference и результаты существующей версии.

**Рекомендованная настройка Codex:** GPT-6.1 Sol, reasoning High.
Это стартовая рекомендация для работы с кодом, происхождением меток и метриками,
а не измеренный результат сравнения моделей на GoodsAI. Более дорогая
альтернатива для отдельного сложного аудита — GPT-6 Astra, reasoning High.
Extra high/Max применять только при показанной пользе на наших задачах.
Основание: [модель GPT-6.1 Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol)
и [рекомендации OpenAI по reasoning](https://developers.openai.com/api/docs/guides/deployment-checklist).
Выбор модели Codex не означает разрешения на внешние API-вызовы из GoodsAI.

Ниже — инструкции агенту. Для начала достаточно попросить прочитать этот файл
и выполнить описанный этап.

## Цель и границы

Продолжи GoodsAI как ML/NLP Engineer и Software Engineer. Получи первую
воспроизводимую оценку **существующего rules baseline** на проверенной человеком
части reference и подготовь error analysis. Пиши по-русски, действуй по текущему
репозиторию; язык проекта — Python, не создавай новый Java/backend-проект.

На этом этапе не улучшай правила извлечения, не обучай модель и не добавляй
LLM в pipeline. Сначала нужна неизменная точка отсчёта. Не создавай новый
120-карточный набор и не проси пользователя проверять оставшиеся 96 подряд.

## Шаг 1. Сведи решения и зафиксируй reference

Проверь семь частичных карточек: R03, R04, R17, R19, R21, R22, R23.
Наличие решения AI по источнику не равно человеческому подтверждению.

- R17: предложен Galaxy Line, написанный в title и подтверждённый официальной
  карточкой. Старое отдельное Galaxy не переименовывать автоматически.
- R21: предложен серебристо-черный по правилу составных цветов.
- R22: выбран TWK4P439 без бренда, линейки и технического CTWK34A.
- R23: выбран KRWK02, прямо указанный как модель в инструкции и нашем title.
- R03: десятичное TB→GB и трактовка RAM требуют зафиксированной политики;
  внешнее подтверждение 16 GB от пользователя сохранено отдельно. Не считать
  вопрос «как думаешь?» согласием на произвольное изменение всех меток.
- R04: не назначать GB голым числам универсально. Трактовка 8/512 хранится
  отдельно; строгую неоднозначность можно оставить исключённой из оценки.
- R19: не исправлять «объём в кг» на литры молча. Сведения пользователя с сайта
  не становятся буквальным свидетельством в разрешённом текстовом входе.

Согласованные правила: 5G сохраняется в явно написанном имени модели;
конфликт разных источников требует review; известные оттенки/составные цвета
могут быть строковыми значениями. При наличии цветового сигнала неизвестный
оттенок — ambiguous/review, а не absent только из-за отсутствия алиаса.
Контекстные RAM/storage-гипотезы не включаются в строгую оценку как present.

Проверь единообразие канонических брендов/единиц/цветов по утверждённой схеме.
Например, различие регистра бренда не должно случайно определять результат.
Нормативную канонизацию устанавливай до чтения predictions: не переписывай
reference под ошибки baseline. Исправления оформляй новой версией с причиной
и происхождением; неизвестные договорённости не восстанавливай по догадке.

Если для частичных случаев всё ещё нужен ответ пользователя, подготовь один
компактный список конкретных решений/вопросов. Независимую работу не останавливай:
заморозь для предварительной оценки уже допустимые полные проверки. Не обещай
24 полностью проверенные карточки при фактических 17.

Оригиналы не перезаписывай. Создай отдельные development/validation reference
JSONL и manifest с hashes исходников, правилами включения/исключения, списком
SKU, составом категорий и количеством статусов. Все реальные записи — в data/,
отчёты с деталями — в outputs/, вне Git. Частичные карточки не повышай до
reviewed/manual только ради увеличения числа записей.

## Шаг 2. Проверь границы и идентичность baseline

До вычисления метрик проверь:

- уникальность SKU, совпадение category/title/description и сохранение split/group;
- порядок и состав атрибутов, канонические числа/единицы и точные raw evidence;
- происхождение reference: какие решения подтверждены человеком, какие
  исключены, какие остаются AI или внешними уточнениями;
- наличие predictions для всех включённых SKU, отсутствие дублей и ошибочных
  статусов; сопоставимость schema/config/code hashes с существующим manifest;
- development/validation разделены, test_reserved не используется для настройки.

Не запускай prepare/annotate без необходимости: они создают производные файлы.
Если исходные predictions совместимы, используй их для первого замера.
Если требуется повторный predict, сохрани его отдельно и укажи, почему старый
результат не подходил. Не перезаписывай исходные predictions/manifests.

## Шаг 3. Посчитай первую оценку

Используй существующий manual-reference evaluator, предварительно проверив
его семантику. AI-reference режим для этого этапа не нужен. При необходимости
исправляй только подтверждённую ошибку расчёта/валидации с отдельным тестом;
правила извлечения и политика меток остаются заморожены.

CLI для каждого split отдельно (пути заменить на реально созданные):

```powershell
.\.venv\Scripts\python.exe -m goodsai.cli evaluate --predictions outputs/baseline/predictions.jsonl --gold data/gold/e1/reviewed/<version>/validation.jsonl --output outputs/evaluation/<version>/validation.metrics.json
```

Сохрани P/R/F1 по каждому атрибуту, категориям и категория×атрибут; TP/FP/FN,
support, coverage с явным знаменателем, число исключённых ambiguous/unjudgeable,
пропущенные predictions и invalid statuses. Для undefined метрик оставляй
N/A/null, не заменяй их нулём или единицей для красивой таблицы.

Назови результат «оценка на AI-assisted human-reviewed validation subset».
Укажи малый размер, неслучайный отбор review и участие автора baseline в разметке.
Не называй его независимым test/gold, не объединяй с development или всеми
120 AI-строками. Coverage кандидатов review не выдавай за точность или за
долю безопасно автоматически записанных в каталог значений.

## Шаг 4. Подготовь error analysis и передачу следующего этапа

Сначала анализируй development-ошибки: извлечение, нормализация, конфликт,
отсутствующее правило, ошибочный/недостаточный источник. Не меняй метки из-за
несовпадения с прогнозом. Предложения исправлений обосновывай development;
validation-отчёт сохраняй как проверку, не перебирай по нему правила и пороги.
Этот validation уже участвовал в обсуждении инструкции — не называй его
нетронутым holdout. Для независимого финального замера потребуется новый
слепой человеческий reference с аудитом дублей; текущий test_reserved сам по
себе ещё не является размеченным независимым тестом.

Реальные карточки/цитаты/по-SKU ошибки сохраняй только локально. В
`docs/research/first_baseline_evaluation.md` запиши агрегаты, определения,
reference/model hashes, объёмы, ограничения и 3–5 следующих приоритетов.
Отдельно обозначь всегда отсутствующий model, перенос согласованной цветовой
политики в runtime и необходимость последующего ML **или** LLM-эксперимента.
Проверь пересечение с работой участников из TEAM_TASKS; не перезаписывай их
прототип/аудит или незакоммиченные изменения.

Обнови PROJECT_STATUS и ссылки на актуальные версии. Для данных достаточно
содержательной проверки invariants/hashes; при изменении общих модулей запусти:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Не отправляй реальные данные внешним API, не запускай платные модели или VM,
не делай commit/push/PR/merge без отдельного запроса. Не добавляй инфраструктуру
или новые категории в ходе этой оценки.

## Критерий завершения этапа

Есть зафиксированный допустимый reference с происхождением и split, проверенное
соответствие predictions, отдельные dev/validation-метрики, error analysis и
отчёт с ограничениями. Незакрытые вопросы не скрыты и не блокируют оценку
доступной проверенной части. В финальном ответе сообщи реальные объёмы и
результаты, пути к отчётам, что проверено и какое следующее улучшение обосновано.
На этом этап завершён; внедрение улучшений и ML/LLM — следующие отдельные шаги.
