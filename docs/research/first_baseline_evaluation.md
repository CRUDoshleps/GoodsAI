# Первая оценка rules baseline GoodsAI

17 октября 2026 года. **Оценка на AI-assisted human-reviewed validation subset**:
8 карточек, 48 допустимых пар, TP=22 / FP=1 / FN=14, precision **95,7%**,
recall **61,1%**, micro-F1 **74,6%**. Это первый ориентир для текущей версии,
не независимый gold/test и не оценка всего каталога. Правила и evaluator не изменялись.

## Reference и границы вывода

Из 120 AI-карточек использованы только 17 полностью проверенных пользователем
записей `review.human-reviewed.v5.jsonl`. Заморожена новая локальная версия
`data/gold/e1/reviewed/reviewed-v1/` с отдельными JSONL development/validation,
`canonicalization.json` и `manifest.json`. Оригиналы не перезаписаны.

`Unjudgeable` в включённых карточках нет. Семь частичных проверок

Контекстные интерпретации памяти сохранены как provenance, в present не включены.

До открытия predictions выполнена только механическая канонизация трёх
брендовых меток: два изменения регистра для CENTEK, одно для TECNO. Источник —
ключи уже существующего `baseline.json`; новые aliases не вводились. Единицы,
числа, модели, цвета, исходные spans и смысл ручных подтверждений не менялись.
Исходная версия и причина каждой замены сохранены. Цветовые оттенки и составные
значения оставлены по согласованной политике, даже если runtime их не извлекает.

Отбор review неслучаен; категории и бренды малочисленны и несбалансированы.
Разметку предложил тот же AI-автор, что участвовал в baseline, затем её проверял
пользователь. Validation уже участвовал в обсуждении инструкции и не является
нетронутым holdout. Даже 100% precision на отдельных срезах не доказывает
надёжность автоматической записи. Интервалы неопределённости не вычислялись;
выборки недостаточно для калибровки или выводов о редких продавцах/категориях.

## Определения

Единица — `(SKU, attribute)`. Judged — только present/absent, support — число
present. Правильное каноническое value+unit даёт TP; неверное значение — FP+FN;
выдача на absent — FP; пропуск present — FN. Отказ на absent не повышает F1.
Precision=TP/(TP+FP), recall=TP/(TP+FN), F1=2TP/(2TP+FP+FN).
Нулевой знаменатель остаётся null/N/A, не заменяется 0 или 1.
Точный raw span проверяется на обоих входах, но отдельная span-conditioned
normalization-метрика evaluator пока не реализована.

Candidate coverage в следующих таблицах — predicted/judged; correct coverage —
TP/judged. Это кандидаты `decision=review`, confidence эвристический.
Автоматически принятых атрибутов **0**. Coverage не равен precision.

## Error analysis и следующие приоритеты

Предложения основаны на **development**, без изменения reference по predictions
и без перебора правил/порогов по validation. В development 17 ошибочных пар:
все FN, TP=18, FP=0. Подробные тексты и SKU находятся только в локальных
`development.pairs.jsonl` и `development.error_analysis.jsonl/.md`.

| Причина по development | FN | Вывод для следующего этапа |
| --- | ---: | --- |
| Нет extractor model | 8 | Самый большой наблюдаемый источник пропусков; отдельный прототип участника B |
| Нет явного бренда в словаре | 3 | Нужен управляемый справочник с происхождением, без угадывания бренда по модели |
| Нет нормализации цвета/оттенка | 3 | Runtime отстаёт от согласованной цветовой политики |
| Вариант записи единицы батареи | 1 | Проверить допустимые написания и точные spans |
| Максимальная вместимость отклонена как неопределённая | 1 | Разделить номинальный максимум ёмкости и произвольный диапазон по контексту |
| Разорванная десятичная запись порождает ложный конфликт | 1 | Не захватывать хвост числа как самостоятельное значение |

Проверка кандидатов Rules на development подтвердила ложный конфликт чисел;
это дефект извлечения/разбора исходной записи, не причина менять ручную метку.
Фильтр неопределённости также консервативно отбрасывает указанную максимальную
вместимость. Успешные отказы при недостаточном тексте и ambiguous-пары показаны
отдельно, не записаны в FN.

На validation зарегистрированы 14 ошибочных пар: 13 пропусков и одно неверное
число (оно даёт одновременно FP+FN). По атрибутам FN: model 8, color 3,
battery/screen/capacity по 1. Детали сохранены в `validation.pairs.jsonl`;
эти наблюдения не использовались для внедрения или подбора исправлений.

Пять приоритетов следующего отдельного этапа:

1. Подготовить и интегрировать консервативный model-прототип из потока B:
   явное имя/код, точный span, отказы при нескольких кодах. Development даёт 8 FN.
2. Перенести согласованную цветовую политику в runtime: известные оттенки и
   составные цвета, неизвестные сигналы и конфликты отправлять на review;
   дополнить обоснованный словарь брендов. На development это 6 FN.
3. Исправить подтверждённые development-проблемы числового извлечения и единиц
   с синтетическими regression tests; это 3 FN. Не угадывать GB для любых чисел
   и не переводить kg→L как «нормализацию».
4. Завершить 7 частичных решений отдельной версией; участнику C — полный аудит
   близких дублей. Для финального замера собрать новый слепой человеческий
   reference: текущий test_reserved ещё не размечен и не независим автоматически.
5. После фиксации следующей версии сравнить rules с одним ML **или** LLM-методом
   на одинаковом split; качество, FP, latency и стоимость показать раздельно.
   Разметка с помощью AI не заменяет этот эксперимент. Доступ/бюджет и внешняя
   передача данных требуют отдельного решения. Участнику A остаётся Linux-прогон.

Прототип B и общий аудит C не редактировались; shared runtime и схема заморожены.
Калибровка и автоматическая запись не вводились. Текущие buckets evaluator
`0.7` означают [0.7,0.8), `0.8` — [0.8,0.9), а не scores ровно 0.7/0.8:
на development 1/1 и 17/17 верных, на validation 3/3 и 19/20. Малые support,
исключённые ambiguous и зависимость разметки не позволяют подобрать надёжный
порог. Traffic-weighted метрики и fairness по продавцам не вычислены:
семантика весов/идентификаторы и достаточная разметка не подтверждены.

## Артефакты и воспроизведение

Все реальные reference/ошибки/predictions находятся в игнорируемых `data/outputs`.
В Git предназначены только этот агрегированный отчёт и документы состояния.
Источник reference содержит AI-assisted происхождение, annotator и ledger;
значение `manual_reference` в JSON — режим допуска evaluator, не заявление
о независимом gold.

Исходный набор уже заморожен. Повторить оценку в **новые** файлы можно из корня:

```powershell
.\.venv\Scripts\python.exe -m goodsai.cli evaluate --predictions outputs/baseline/predictions.jsonl --gold data/gold/e1/reviewed/reviewed-v1/development.jsonl --output outputs/evaluation/reviewed-v1/development.check.json
.\.venv\Scripts\python.exe -m goodsai.cli evaluate --predictions outputs/baseline/predictions.jsonl --gold data/gold/e1/reviewed/reviewed-v1/validation.jsonl --output outputs/evaluation/reviewed-v1/validation.check.json
```

Локальный `outputs/evaluation/reviewed-v1/run_stage.py` сохраняет алгоритм
freeze → measure, проверенные hashes, CLI argv и exit codes. `build_report.py`
сохраняет development-диагнозы и формирует этот отчёт; оба скрипта запрещают
перезапись своих артефактов. Повторная фиксация требует нового пути/версии.
На машине без локальных data/outputs эти команды не выполнятся: метки и данные
не поступают из Git автоматически. Полный lineage и списки SKU/group/status
находятся в reference manifest; сам отчёт не заменяет их.
