# Следующая задача: воспроизводимое демо и индекс результатов

18 октября 2026, Europe/Moscow. Статус: **реализовано и проверено локально на Windows;
пользователь разрешил commit/push feature-ветки; main и ВМ этим этапом не обновлялись**.
Основание: R1 и публичная часть R2 из [плана после ревью](post_review_plan.md).
Рабочая ветка: `feature/vlad-reproducible-demo`, база — актуальный origin/main.

## Почему эта задача следующая

Проверяющий должен без датасета получить реальный JSONL-результат, manifest
и понятную сводку из одной команды. Сейчас Linux-пример есть в README,
но он требует ручного shell-сценария, ожидаемый ответ описан лишь частично,
а метрики/артефакты разбросаны по документам. Это небольшой завершённый PR
для замечаний о воспроизводимости и подаче результата (по 0,44 недобора),
а также подготовки ещё не оценённого блока качества.

Эта задача улучшает демонстрацию и проверяемость, не обещает роста recall/F1.
После неё следующий функциональный пакет — verifier/model и модельный эксперимент;
оформление демо не должно растягиваться на несколько этапов вместо этого.

## Ожидаемый результат

После обычной установки пользователь выполняет одну команду на Windows/Linux:

```bash
python -m goodsai.demo --output-dir outputs/demo
```

Команда реализована в `goodsai.demo` и проверена в editable- и чистой wheel-установке.
Python вызывается из `.venv`; отдельные shell-скрипты для двух ОС не нужны.
Команда запускает то же ядро/CLI predict, а не копию правил или готовый ответ.

Выходы в новом каталоге:

- `input.jsonl` — копия явно синтетического входа;
- `predictions.jsonl` и существующий prediction manifest;
- `summary.json` — статусы, причины отказов, счётчики и результаты проверок
  заявленных примеров, ссылки/хеши созданных файлов; не отчёт качества каталога.

Артефакты генерируются локально в игнорируемом outputs. В Git — только
синтетический вход, реализация, тесты, документация и агрегированные результаты.

## Шаги реализации

1. **Синтетические сценарии.** Добавить явно вымышленные карточки в
   `src/goodsai/examples/synthetic/products.jsonl`: смартфон с явными характеристиками,
   чайник с нормализацией единиц, конфликт значений, отсутствие характеристик,
   неизвестная категория, нарушенный Product-контракт. Писать новые примеры,
   не переносить реальные SKU/названия/описания из data или gold.
2. **Runner.** Добавить `src/goodsai/demo.py`, переиспользовать load_config,
   predict и существующие manifest/validator. Проверять ожидаемые статусы,
   ключевые values/units, review/abstain и raw evidence. Не фиксировать полный
   output hash: code identity меняется между релизами. run_id и SHA должны
   вычисляться действующим pipeline, а не подставляться из документации.
3. **Безопасное назначение.** Новый output-dir создаётся эксклюзивно;
   повторный запуск в уже существующий каталог завершается понятной ошибкой
   и не затирает артефакты. Путь внутри raw/входа запрещён. Не исправлять
   глобальный atomic_text в этом PR: конкурентная запись — отдельная R3.
4. **README.** Короткая инструкция для двух ОС, одна команда, имена выходов,
   полный JSON одного синтетического ответа и расшифровка evidence/confidence/
   decision. Прямо показать model=null, unknown category и invalid_input.
   Объяснить: обработанная строка не обязательно означает заполненные атрибуты;
   все кандидаты требуют review, эвристическая уверенность не вероятность.
5. **Индекс артефактов.** Создать `docs/DELIVERY_INDEX.md`: шесть требований
   сдачи, что реализовано, путь/команда/источник/версия и открытые пункты.
   Связать EDA, демонстрацию, реальные reviewed-v2 метрики, локальный prediction
   manifest и техническую презентацию, которая ещё не готова. Не объявлять
   продуктовую презентацию финальным техническим результатом.
6. **Метрики в README.** Сослаться на существующий immutable reviewed-v2;
   кратко указать 12 validation-карточек, 67 judged-пар, P=96,7%, R=58,0%,
   F1=72,5%, происхождение AI-assisted и отсутствие независимого holdout.
   Синтетическое демо не использовать для новых P/R/F1. Полную реальную выдачу
   и reference не публиковать; канал сдачи остаётся отдельным вопросом.
7. **Проверка.** Интеграционный тест runner на временном каталоге: артефакты
   согласованы, ключевые исходы верны, повторный запуск не перезаписывает данные,
   результат воспроизводим при одинаковых коде/config/input. Выполнить baseline
   suite и demo smoke; проверить запуск из другой рабочей директории и наличие
   синтетических ресурсов в установленном пакете. Добавить ресурсы в package
   data либо выбрать доступный в установленном пакете источник без дублирования.
8. **Завершение.** Обновить PROJECT_STATUS, показать diff и фактические проверки;
   реализацию передавать отдельным PR. Linux/VM smoke подтверждать отдельно
   от локального Windows. Менять работающую ВМ только в разрешённом объёме.

## Готовность и границы

Задача закрыта, когда чистая установка и одна команда дают проверенные JSONL,
manifest и summary; README содержит полный вход/выход и честные метрики,
а индекс связывает реализованные артефакты с воспроизведением. Пустая ссылка
или текст «сгенерируйте сами» вместо исполняемой команды недостаточны.

В этом PR нет изменений схемы v0.1, правил извлечения, confidence/decision,
нового API, внешних моделей или публикации реальных данных. Добавление модуля
изменит будущий code hash CLI, но исторические benchmark/reference остаются
неизменными. Отсутствие канала выдачи реальных predictions остаётся открытым
пунктом R2, даже после успешной реализации синтетического демо.
