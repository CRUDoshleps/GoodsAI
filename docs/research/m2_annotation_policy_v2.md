# M2: согласованная политика разметки v2

Актуальная локальная версия — policy-v3: пользователь подтвердил уточнение
неизвестных слэш-суффиксов в round6. Если роль/граница суффикса неясна по
разрешённому тексту — model ambiguous; явное обозначение полного индекса как
модели может позволять сохранить его целиком. Универсального правила удаления
после слэша нет; внешнее знание сохраняется отдельно. Остальные правила v2 ниже
сохранены. [Все 20 карточек подтверждены и оценены](m2_evaluation_results.md).

Три правила и приоритет конкретного цвета согласованы пользователем после
первой партии M2. Это политика reference, не изменение runtime v0.1.
История обсуждения — [round1](m2_round1_policy_notes.md).

## Действующие уточнения

1. **Бренд:** более конкретный явно написанный согласованный суббренд вместо
   материнского бренда, если оба обозначают сам товар. Сейчас согласована связь
   Xiaomi → Redmi. Не достраивать ненаписанный бренд по знаниям модели/SKU;
   не считать любое соседнее слово суббрендом. Выбранный бренд не дублируется
   в model. Другие связи требуют отдельного обоснования.
2. **Модель:** явное основное коммерческое имя без бренда, памяти, цвета,
   состояния и отдельно описанных функций. Дополнительный код — в заметке,
   когда основное имя однозначно. Не удалять все скобки/индексы: код может быть
   единственным именем модели. При неясной границе — ambiguous/abstain.
   Прежняя минимальная нормализация символов/регистра не меняется.
3. **Память:** одна емкость с GB без указания роли — ambiguous, без догадки по
   величине числа. Явные storage/RAM-контексты и согласованные связные пары
   RAM/ROM с единицей сохраняются. Пары без единиц и конфликты — ambiguous.
   Это правило роли, не новое правило числовой нормализации. Ранее согласованные
   Gb → GB в контексте емкости памяти и десятичное TB → 1000 GB сохраняются.
4. **Цвет:** единственный конкретный цветовой вариант можно предпочесть общей
   пометке «многоцветный». Это согласованный приоритет, не доказательство того,
   почему продавец написал общую пометку. Сохранять оба сигнала в evidence.
   Два конкретных противоречащих цвета не разрешаются этим правилом.
   По материалу корпуса цвет не выводится. «Титановый» — допустимое имя явно
   цветового варианта, не утверждение о титане или сером цвете.
5. Согласованное в round1: непонятный маркетинговый модификатор не мешает
   выбрать один явно названный базовый цвет; полная фраза остается в evidence.
   Узнаваемые оттенки сохраняются, «ультрамарин» принят как русский алиас.

## Почему строгий эталон не равен большой очереди review

В reference ambiguous означает недостаточную определённость по инструкции.
Это не команда отправить каждую такую карточку человеку в production.
Сейчас все непустые runtime-кандидаты уже имеют decision=review, а abstain
не реализует отдельную очередь. M2 не меняет эти решения.

В новых 20 development-карточках правило одиночной емкости меняет два
storage-поля у смартфонов. Это описание отобранной партии, не оценка доли
проблемы во всём каталоге. Проверенная ранее reviewed-v2 содержит 22 карточки;
по этим уточнениям новых изменений меток там не обнаружено. Старые файлы
сохраняются как исторические, а AI-only 120 не объявляются заново проверенными
по новой политике. Предсказания не использовались для принятия этих решений.

Для будущего runtime можно сравнить два варианта:

| Подход | Польза | Ограничение |
| --- | --- | --- |
| Явная роль / согласованная пара, иначе отказ | Прозрачное обоснование роли, меньше предположений | Потеря извлекаемости на неполных заголовках |
| Контекстный ML/LLM-кандидат для ручной проверки | Может покрыть часть неподписанных объемов | Допущение не становится фактом; нужен отдельный измеренный опыт |

Рекомендация: сохранить строгую инструкцию эталона; контекстные гипотезы
испытывать отдельно в разрешённом будущем модельном этапе. Не направлять
автоматически все отсутствующие сведения в ручную очередь; при её будущем
проектировании отбирать спорные кандидаты, проверять поле, а не всю карточку,
и объединять повторяющиеся проблемы шаблона продавца. Такая очередь сейчас
не реализована и сама по себе не меняет confidence/decision.

## Метрики и происхождение

Ambiguous исключаются штатным evaluator из judged P/R/F1; это может изменить
support и видимые метрики без улучшения модели. Обязательно показывать число
исключений, долю judged, coverage на всех применимых парах и ошибки/необоснованные
выдачи на неоднозначных парах отдельным диагностическим списком. Не считать
abstain на ambiguous новым TP/TN. Сравниваемые методы оценивать на одной версии
reference; результаты разных инструкций не выдавать за прирост runtime.
Новые метрики пока N/A, predictions не запускались.
