## Источники требований и границы выводов

**Условия кейса:** [PDF кейсодателя](../product-stage/context/case/attribute-extraction-case.pdf),
стр. 10, 16–18: только текст; извлечение и нормализация обязательных атрибутов;
начать с правил/словарей, затем попробовать ML или LLM; честные per-attribute
P/R/F1; шесть артефактов сдачи. Стр. 5 отдельно указывает coverage, traffic-weighted
оценку и ручной gold-set. [Текст платформы](../product-stage/context/case/platform-requirements.md)
сохранён командой 14 октября; он не является свежей проверкой сайта организаторов.
Подробная балльная шкала технического отбора в просмотренных материалах не найдена.

**Прежние гипотезы команды:** обязательный ruBERT/QA encoder, многоуровневый LLM
router, точная таксономия обязательных полей и доступность обучающей разметки.
Это не следует автоматически из условий. Стр. 17 обещает CSV/JSON и размеченную
часть, но фактически предоставлены Parquet и YML-подобный pickle без выделенного
gold/split. Расхождение требуется уточнить у организаторов.

**Рекомендации по результатам EDA:** в [архитектуре и контракте](architecture_and_contract.md),
[стратегии оценки](evaluation.md), [плане до 23 октября](implementation_plan.md).

## Метод и доказательства

1. Метаданные и схемы обоих Parquet прочитаны PyArrow; проверены все row groups.
2. Полные агрегаты посчитаны DuckDB с `memory_limit=768MB`, двумя потоками и
   временным каталогом в `outputs/eda/`. Длинные описания сравнивались по MD5:
   это диагностика повторов по fingerprint, не доказательство побайтовой идентичности.
3. Пользователь подтвердил официальный источник pickle и разрешил загрузку.
   Полный первый проход `pickletools` обнаружил только контейнеры, строки и
   служебные команды протокола 4, без GLOBAL/REDUCE/BUILD. Затем специальный
   последовательный reader обработал все товары, сохраняя только 57 реально
   используемых memo-ссылок из 94 439 553 записей memo. Полный объект не загружался.
   Синтетические тесты проверяют совпадение с обычным pickle, границы пакетов,
   отказ при разделяемых изменяемых объектах и создании классов.
4. Выбраны 200 карточек с описанием из каждой из пяти категорий: смартфоны,
   чайники, ноутбуки, телевизоры, мониторы. Выборка детерминирована по
   `md5(sku_id + ':goodsai-eda-v1')`. Это диагностические 1 000 карточек,
   не размеченный gold-set и не случайная оценка всего каталога.
5. После чтения SHA-256 всех трёх оригинальных файлов совпали с inventory,
   составленным до EDA. Содержимое raw-файлов сохранилось.

Машиночитаемые доказательства **локальны и исключены из Git**:
`outputs/eda/parquet_profile.json` (включая статистики row groups),
`catalog_profile.json`, `joins_profile.json`, `pickle_opcodes.json`.
`inspection_sample.json` содержит выбранные реальные тексты и поля; его нельзя
публиковать. `catalog_skus.parquet` — локальная компактная проекция каталога;
`profile.duckdb` — служебные агрегаты. Ни один из них не является результатом модели.

### Описания

Полные данные (`parquet_profile.json`, разделы `descriptions`, `text_duplicates`):

- Все 1 177 200 `sku_id` уникальны; NULL и пустых после trim title/description нет.
- Длина title: минимум 7, медиана 43, p90 75, p99 124, максимум 288 символов.
- Длина description: минимум 3, медиана 630, p90 1 440, p99 2 737, максимум 27 525.
  Отсутствие пустых строк не означает содержательное описание.
- 580 505 описаний содержат HTML-подобные теги (49,31%), 389 499 — переводы строки.
  В одном описании есть символ замены U+FFFD.
- 484 361 повтор заголовка сверх первого вхождения; 260 320 повторов непустого
  описания по MD5 сверх первого. Полных дублей строк нет, что также следует
  из уникальности SKU. Повторы текста между SKU важны для split.

### Каталог и параметры

`catalog_profile.json` и `joins_profile.json/catalog`:

- Корневой timestamp каталога: `2026-05-13T03:00:00+0000`. У остальных файлов
  явного времени события/снимка в схемах нет; синхронность файлов не доказана.
- `@id`, `@available`, `vendor`, `model`, `name` — строки. ID уникальны.
  `@available` тоже строка, не готовый boolean.
- `categories` — объект с `categoryId`. У каждого обследованного товара одна
  категория. В справочнике 6 963 уникальных ID, ссылки на родителей корректны;
  товары используют 3 599 ID. Четыре ID отсутствуют в справочнике:
  `56657` (20 товаров), `34808` (14), `27770` (4), `33313` (1).
- Названия категорий не уникальные ключи: например, «Смартфоны» есть у родительского
  ID 205 и товарного ID 761. Использовать ID и родительские связи, не имя.
- Нет `vendor` у 11 товаров, `model` у 5; ещё 42 модели — строковые placeholders.
  Поле `name` заполнено у всех. В каталоге 6 765 разных строк vendor и 420 491 model.
- `param`: список у 546 040 товаров, одиночный объект у 29. Элемент содержит
  `@name`, `#text`, иногда `@unit`. Медиана числа элементов — 27, p90 — 71,
  p99 — 169, максимум — 301; всего 12 999 разных имён параметров.
- В 148 871 карточке повторяются имена параметров. Это могут быть множественные
  значения/варианты фильтров; считать их автоматически ошибками нельзя.
  Обнаружен один пустой `#text`. Не превращать список в обычный dict с потерей дублей.
- `Продавец` встречается в 545 741 карточке: 2 048 разных строк, ещё 328 без поля.
  Это имя/обозначение продавца, не подтверждённый стабильный seller ID.
- 41 884 группы повторяющихся `(vendor, model)` дают 119 217 дополнительных
  карточек. Эти группы нужны для контроля утечки между split.

### Файл с запросами и кликами

Реальные колонки: `sku_id`, `sku_subject_id`, `sku_seo_id`, `sku_position` — uint64;
`sku_price` — double; `toValidUTF8(sku_name)`, `toValidUTF8(sku_brand_name)`,
`toValidUTF8(query_text)` — large_string. Имена с `toValidUTF8(...)` — буквальные
имена колонок, их нужно корректно экранировать или переименовать в адаптере.

Полные агрегаты: 332 753 уникальных SKU, 1 789 579 уникальных строк запроса,
4 103 subject ID и 4 101 seo ID. NULL нет, но пустые sku_name встречаются
в 6 740 032 строках, brand_name — в 8 791 897, query_text — в трёх.
Цена от 0 до 11 900 000; 116 391 строка с нулевой ценой. Позиции 0–5 893,
из них 7 385 481 нулевые. Нулевая позиция может быть началом отсчёта или
служебным значением — её значение не установлено.

В первых 100 000 физических строк 12 495 точных повторов сверх первого.
Это **не** полная оценка дублей и **не** основание удалять повторные события.
Нет столбцов `click`, `click_count`, `impressions`, timestamp, user/session ID.
Название файла предполагает кликовые наблюдения, но точная единица записи
должна быть подтверждена организаторами. Запрос не является фактом о товаре.

## Связи и качество соединений

Приводить ID к строковому контракту; в аналитическом join допустимо проверенное
приведение к BIGINT/UBIGINT. Не соединять по заголовку или имени модели.

| Связь | Результат полного join |
| --- | --- |
| Каталог ↔ описания по SKU | 241 355 совпавших SKU; 304 714 товаров каталога без описания; 935 845 описаний без каталога |
| Каталог ↔ кликовые SKU | 241 661 из 332 753 SKU; 28 869 133 строк наблюдений |
| Описания ↔ кликовые SKU | 158 158 из 332 753 SKU; 19 774 145 строк наблюдений |
| Все три файла | 102 945 общих SKU |

У 44 102 из 241 355 совпавших SKU `name` каталога и `title` описаний различаются.
Это не доказывает ошибочный join, но требует сохранения обоих исходных полей,
флага расхождения и выборочной проверки; не перезаписывать один текст другим.
В пилоте primary title = `skus.name`, description = `sku_desc.description`;
другой title хранится для аудита и пока не используется для извлечения.

Для 11 216 кликовых SKU встречается несколько subject ID; для 11 255 — несколько
seo ID. У сопоставленных с каталогом SKU постоянный seo совпадает с категорией
в 230 124 случаях, постоянный subject — в 89 388. Это разные поля, заменять
ими `categoryId` автоматически нельзя. Источник категории пилота — каталог.

## Что значат готовые характеристики

Существующие поля — хороший материал для схемы, словарей и weak labels.
Независимая эталонная разметка, отдельные splits, span-разметка, списки обязательных
полей и закрытые нормативные словари в исследованных структурах не обнаружены.
Наблюдаемые значения каталога — эмпирический словарь, не официальная таксономия.

Небольшие проверенные примеры из диагностической выборки:

- SKU `30070153`: `Диагональ экрана = 6.2 - 6.5"`, а `Диагональ_search = 6.5`
  с единицей `"`; текст содержит «6,5 дюйма». Диапазон фильтра и точное значение
  нельзя оценивать как одну и ту же строковую метку.
- SKU `20062333`: `Объем воды = от 1.6 до 1.8 л`, `Максимальный объем_search = 1.7 л`,
  в описании «1,7 л». Десятичная запятая требует нормализации.
- SKU `20057603`: мощность в тексте записана как `2 400 Вт`, поле — `2400` + `Вт`;
  «нержавеющая сталь» встречается как значение цвета, хотя это ещё и материал.
- SKU `30070642`: `Цвет = синий`, `Цвет_search = темно-синий`, в названии `Blue Black`.
  Уровень детализации канонического цвета необходимо согласовать.

В 200 выбранных смартфонах строка `Встроенная память (ROM)_search` буквально
нашлась в названии/описании в 90 из 200 случаев, `Диагональ_search` — в 9 из 197,
`Цвет_search` — в 77 из 197. Для 200 чайников мощность `_search` найдена буквально
в 124 из 169, максимальный объём — в 20 из 169. Это **не качество извлечения**:
числа отличаются пунктуацией и единицами, а совпавшее число может относиться
к другому свойству. Проверка только показывает, почему нужны нормализация и
контекстная проверка. Счётчики прочих атрибутов в JSON считаются по элементам
param и могут превышать число карточек из-за повторов.

## Воспроизведение

Из корня GoodsAI, PowerShell, Python 3.12:

```powershell
.\.venv\Scripts\python.exe -m pip install -r scripts/research/requirements.txt
.\.venv\Scripts\python.exe scripts/research/profile_parquet.py
.\.venv\Scripts\python.exe scripts/research/inspect_pickle.py data/raw/skus.pkl outputs/eda/pickle_opcodes.json
.\.venv\Scripts\python.exe scripts/research/profile_catalog.py --trusted-pickle
.\.venv\Scripts\python.exe scripts/research/profile_joins.py
.\.venv\Scripts\python.exe -m unittest discover -s scripts/research -p 'test_*.py' -v
```

Флаг доверия разрешён пользователем для имеющегося официального файла. Для
другого pickle сначала подтвердить происхождение. Reader использует частный
CPython API и проверен на 3.12.6, отказывается от неподдерживаемых opcodes или
ссылок на изменяемые объекты; не считать его универсальным загрузчиком.
Перед повторным чтением сверяет SHA-256 с первым проходом.

Скрипты пишут только исследовательские результаты в `outputs/eda/`; повторный
запуск обновляет эти результаты. Запускать последовательно из корня, не параллельно
с другим писателем `profile.duckdb`. EDA не требует pandas, torch или transformers.
Пакеты текущего EDA: PyArrow 26.0.0 и DuckDB 1.5.6.
Первый обход pickle занял около 333 с, второй — 159 с на локальной Windows;
это время EDA, не скорость будущего extractor и не замер на VM.

Сортировка длинных строк и SQL-разворачивание всех JSON-параметров превысили
первоначальный лимит памяти; окончательные скрипты используют fingerprints
и пакетную агрегацию параметров. Сам `memory_limit` DuckDB не гарантирует
общий RSS процесса. Полная проверка на 2 CPU / 4 ГБ остаётся отдельной задачей.

Методические источники: [PyArrow ParquetFile / iter_batches](https://arrow.apache.org/docs/python/generated/pyarrow.parquet.ParquetFile.html),
[Python pickle: доверенность и десериализация](https://docs.python.org/3/library/pickle.html).
