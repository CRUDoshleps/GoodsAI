## 1. Решение и основания

Первый полезный результат — консервативное извлечение явно написанного `model`
для смартфонов и чайников, минимальная проверка его происхождения и измерение
изменений. Это один законченный инкремент: правила + проверки + тесты + отчёт.
Большой универсальный verifier, калибровка и auto_accept не предшествуют ему.
Следующий результат — реальный ограниченный эксперимент rules → LLM через
выданный организаторами шлюз для неразобранных моделей; его интеграция зависит
от измеренного качества и соблюдения бюджета.

команды». Прежнее предположение о неизвестном доступе исправлено. Приоритет —
этот контур организаторов, локальная загрузка весов остаётся резервом.
Это план интеграции; ключи/окружение ВМ не читались, запросы не выполнялись.

презентация, калибровка и независимая итоговая оценка. LLM для двух категорий
сама по себе не доказывает работу на новых категориях или справедливость по продавцам.

## 2. Границы первого инкремента M1

- Python и вход/выход v0.1; категории `761` и `482`, те же requested attributes.
- Кандидат model: строка, `unit=null`, `method=rule`, heuristic score,
  `decision=review`, исходный span; без кандидата — `abstain`.
- Реализованные model-правила без находки используют существующую причину
  `not_found_by_rules`; конфликт — `conflicting_evidence`. Это не заявление,
  что модель отсутствует в тексте. Новые публичные reason_codes пока не нужны.
- Первый охват: однозначные названия/индексы в title и явное поле «Модель: …»
  в description. В описании не извлекать произвольные упоминания устройств.
- Никаких изменений правил памяти/цвета/бренда ради улучшения общей цифры в том
  же сравнении. Согласованные TB, оттенки и полный бренд — отдельные доработки.
- Не использовать готовое поле каталога `model`, другие targets, SKU-lookup,
  интернет-справочник моделей или сохранённые ответы по реальным карточкам.

Первый результат полезен даже без доступа к модельным ресурсам. Нулевые FP на
маленьком dev — критерий продолжения, а не доказательство общей precision=100%.

## 3. Политика model: согласованное и предлагаемое

Подтверждения: [annotation_plan](annotation_plan.md), локальные журналы
`data/gold/e1/ai/review.round3.feedback.json` и `review.round5.feedback.json`.
Последний явно подтверждает R22/R23. Их значения не превращать в таблицу
исключений по SKU, не копировать реальные карточки в тесты.

| Ситуация | Политика и статус |
| --- | --- |
| Бренд + модель | Согласовано: бренд отдельно, в model не дублировать. Не выводить отсутствующий бренд из семейства телефона. |
| Коммерческое имя | Согласовано: сохранять явно написанную серию/версию, значимые слова и индекс. Не оставлять только номер вместо полного однозначного имени. |
| 4G/5G/LTE | Согласовано: сохранять в составе написанного имени; не добавлять из предложения о поддержке сети. Пропущенный суффикс не восстанавливать по знаниям. |
| Память, цвет, состояние | Согласовано: исключать из model. Число модели нельзя отрезать только потому, что оно похоже на память; неизвестный хвост не объявлять цветом. При неясной границе — отказ. |
| Технические коды | R22: TWK4P439, без DesignLine и CTWK34A; R23: KRWK02, без Digitaler Inox. Это согласованные конкретные трактовки, а не универсальное правило «всегда брать алфавитно-цифровой код». |
| Новое имя + серия + несколько кодов | Предлагается: извлекать только явно обозначенное коммерческое имя/модель; если роль кодов неясна, abstain и локальный список для review. Универсальный приоритет кода над именем не утверждён. |
| Совместимость, сравнение, аксессуар | Предлагается: «для …», «совместим с …», «в отличие от …», перечень поддерживаемых моделей и отрицание не являются моделью продаваемого товара. Неоднозначный контекст — отказ. |
| Два разных кандидата | Сохраняем текущий принцип: `conflicting_evidence`, не выбирать title по умолчанию. Совпадающие канонические кандидаты объединять. Короткое имя и имя с 5G автоматически эквивалентными не считать. |
| Только словесное имя или неизвестный бренд | Не запрещены схемой. В M1 принимать при явном маркере «Модель:» и однозначной границе; расширение свободного title — после dev-проверки. Бренд не обязан быть успешно извлечён для явного model. |

**Минимальная нормализация на согласование:** убрать внешние пробелы/разделитель
поля и схлопнуть внутренние пробелы, включая NBSP. Видимые entities декодировать
через существующий offset map. Сохранять регистр, цифры, дефисы, значимые суффиксы;
не склеивать `X 12` в `X12`, не заменять кириллицу латиницей, не транслитерировать.
Не собирать каноническое имя из несмежных полей: один доказуемый непрерывный span.
HTML-теги внутри raw span допустимы, если видимая последовательность непрерывна.
Словари типов конструкций/маркеров допустимы; словарь полных gold-ответов — нет.

До реализации согласовать этот новый общий минимум. Можно принять только
бесспорную часть; тогда спорные имена останутся abstain и будут перечислены
в отчёте. Gold под новое правило не исправлять: изменение аннотационной политики
требует отдельной версии reference и повторного сравнения обоих методов.

## 4. Минимальное усиление verifier

M1 не требует новой архитектуры pipeline. Rules выдаёт Candidate, Extractor
проверяет его и объединяет с остальными, CLI/API сохраняют общее ядро.

1. Перед getattr/срезом проверить attribute из схемы категории, field из
   `title/description`, точные целые offsets (не bool), `0 <= start < end <= len`,
   непустые строки value/text/rule_id, конечный числовой score без bool в [0,1],
   допустимую unit. Для model — null. Ошибка внутренних правил остаётся явной
   ошибкой программы, а не успешным пустым результатом.
2. Для model проверить совпадение raw span и связь с видимой последовательностью
   **полного исходного поля** через offset map. Проверить, что согласованная
   нормализация выбранного фрагмента даёт именно value, без добавленных токенов.
   Не парсить raw подстроку изолированно: можно потерять контекст скрытого HTML.
3. Раздельно проверить допустимость контекста model: совместимость, отрицание,
   чужой товар, память/цвет/служебный код. Проверка преобразования строки полезна,
   но сама по себе не гарантирует правильного смыслового выбора.
4. Сохранить объединение/конфликты и финальный validate_prediction. Закрыть
   обнаруженные нарушения существующих инвариантов (например bool score),
   не добавляя новых полей/decision. При необходимости сверки model в evaluator
   применять чистую проверку нормализации/evidence, **не повторный extractor**:
   иначе оценка станет зависеть от способности правил заново найти ответ.
5. Строгая схема произвольного ответа LLM, duplicate JSON keys, лишние поля,
   лимиты ответа и provenance источника — M3, до реальных model-вызовов.
   Полную переделку output/config validators и числовых правил не включать в M1.

Набор синтетических тестов M1: имя с серией/индексом/5G; 5G только в описании
поддержки; бренд отдельно; явное model без известного бренда; память и цвет рядом;
пустое/неясное имя; два разных имени; повтор одного имени; совместимость,
отрицание, список моделей; технический код с неясной ролью; HTML/entities,
скрытые атрибуты/script; неверные offsets/field/score/unit; настоящий span с
подставленным value. Точные строки придумываются, не копируются из датасета.

Обновить тест `test_no_model_lookup_and_no_card_memory`: он проверяет отсутствие
выдуманных характеристик, а не вечный `rule_not_implemented`. Проверить влияние
на metric fixtures (`Test` как модель), demo expectations и документационные
JSON: старые 11 review / 13 abstain не являются требованием новой версии.
Ожидания обновлять по смыслу синтетического входа, не механически по выводу кода.

### Уже выданный шлюз: источник и настройки

Источник сведений ниже — скриншот пользователя от 18 октября, не API-проверка.

- Base URL: `https://hub.gigaschool.ru/api/v1/llm/v1`.
- Запрос в примере панели: `POST /chat/completions` относительно Base URL.
  Не добавлять второй `/v1`; использовать адрес из `OPENAI_BASE_URL`.
- На ВМ уже заданы `OPENAI_BASE_URL` и `OPENAI_API_KEY`; клиент читает их
  из окружения. Не записывать ключ в config/manifest, Git, тесты или журнал.
- Шлюз заявлен совместимым с OpenAI API; `stream: true` не поддерживается.
  Взаимодействие — обычный завершённый ответ, с явным timeout.
- Дневной лимит команды **100,00 ₽**; на скриншоте потрачено **0,00 ₽**.
  Это снимок, остаток перед будущим опытом проверяется заново. RPM/TPM,
  одновременность, HTTP-ошибки и reset timezone на скриншоте не указаны.
- Цены — ₽ за **1 млн tokens**, вход/выход раздельно; выход включает рассуждения.

| Модель генерации из панели | Вход, ₽/1 млн | Выход, ₽/1 млн |
| --- | ---: | ---: |
| `ai-sage/GigaChat3-10B-A1.8B` | 12,20 | 12,20 |
| `openai/gpt-oss-120b` | 15,86 | 61,00 |
| `GigaChat/GigaChat-3-Pro` | 73,03 | 176,39 |
| `ai-sage/GigaChat3.5-432B-A28B-Reasoning` | 96,22 | 288,60 |

В панели также есть embedding/speech модели; они не заменяют генератор
структурированных атрибутов и в первый fallback не входят. Идентификаторы и
тарифы перед запуском сверить с актуальной панелью, не угадывать алиасы.

Предложение первого опыта — `ai-sage/GigaChat3-10B-A1.8B`: это самый дешёвый
генератор в данном списке, а задача ограничена выделением имени с цитатой.
Это экономический выбор кандидата, не измеренное превосходство по качеству.
Если synthetic/dev-проверка выявит проблемы с выполнением схемы/извлечением,
сравнить с `GigaChat/GigaChat-3-Pro` в том же ограниченном бюджете. Для Pro
панель явно заявляет structured output; поддержку конкретного `response_format`
шлюзом и выбранной моделью всё равно проверить синтетическим запросом.
OpenAI-совместимость не гарантирует все возможности каждого backend.
Неподдержанный strict output не обходить ослаблением локального validator:
использовать строгую проверку JSON или выбрать поддерживающую режим модель.

Reasoning-модель не включать первым default: в панели указаны дополнительные
рассуждения и рекомендация `max_tokens` от 1000, иначе ответ может оборваться.
Для каждого выбранного backend заранее проверить смысл лимита вывода и учёт
reasoning tokens. Тяжёлый режим требует отдельного измерения полезности/цены.

Шлюз расположен вне процесса GoodsAI: наличие ключа на ВМ не означает
локального inference и не даёт оснований объявлять, что тексты не покидают ВМ.
В плане используется конкретный выданный для кейса контур организаторов;
запрет отправки в произвольные сторонние API сохраняется. При реализации
зафиксировать эту узкую границу в проектных инструкциях; доступ к другим
провайдерам не включать автоматически. Ключ не переносить в локальное окружение
без отдельной необходимости. Если фактический runtime — systemd user-service,
проверить наличие переменных именно в его окружении: интерактивный Jupyter/SSH
не доказывает их наследование сервисом. Значения секретов при проверке не выводить.

### Контур реального эксперимента M3

- По умолчанию rules-only. Включаемый hybrid вызывает модель только для `model`
  после `not_found_by_rules` в двух поддержанных категориях. Conflict,
  invalid_input и unsupported_category не направлять на «угадывание».
  Остальные атрибуты не запрашивать; верные или ошибочные непустые rules-ответы
  этот первый router не исправит — ограничение явно измерять.
- Модель получает только разрешённый текст, категорийную схему и инструкцию.
  SKU нужен оболочке для соединения результатов, в prompt не нужен; никаких
  gold/weak labels/provenance. Few-shot — только синтетика или согласованный dev,
  без validation/test. Текст карточки — данные, не команды для агента.
- Ответ — ограниченные кандидаты model с цитатой и полем/позицией либо отказ.
  Строгая JSON-схема ограничивает форму; verifier независимо проверяет текст,
  границы и преобразование. Неоднозначное повторное вхождение цитаты — отказ,
  без fuzzy-поиска «похожего» evidence.
- Сначала candidate validator, затем общий merger. Невалидный model-ответ
  отбрасывается с диагностикой, rules-результаты сохраняются. Timeout, HTTP
  401/403/429/5xx, неверный JSON/schema/span, отказ backend и превышение бюджета не превращаются
  в фиктивный успешный model-ответ. Не ловить все ошибки внутренних правил как
  недоступность модели.
- До запуска согласовать значения `method`/идентификатора источника, причины
  отказов и идентификацию HTTP-run. Нельзя маркировать LLM ответ как `method=rule`
  ради формального сохранения v0.1. Изменение общей семантики — отдельное
  согласование; если совместимое представление не согласовано, публичную
  интеграцию блокируем, v0.1 молча не расширяем.
- Внутренний experiment manifest содержит реальные model_calls, tokens,
  отклонения, версии и времена. Текущий hardcoded `llm_calls=0` заменить в этом
  режиме, не скрывать вызовы. У score фиксировать эвристическое происхождение;
  самоуверенность LLM не является калиброванной вероятностью.
- Предлагаемые ограничения первого опыта: один запрос на карточку без повторов,
  concurrency=1, до 100 уникальных dev-карточек; ограничение входных/выходных
  tokens, timeout и общий wall-time выбрать **до** прогона по синтетике.
  Предлагаемый внутренний бюджет первой итерации — **до 10 ₽**, включая
  синтетические пробы и все сравнения моделей; это часть общего лимита 100 ₽,
  не новый лимит организаторов. Перед каждым запросом резервировать верхнюю
  стоимость ограниченного входа/выхода, учитывать фактический usage и прочие
  расходы команды. При неизвестном остатке/тарифе/usage новые вызовы остановить
  до сверки; ошибки/таймауты могут быть оплачены, не считать их бесплатными.
  Сам локальный счётчик не контролирует расходы параллельных клиентов команды:
  platform cap и предварительная координация бюджета также нужны.
  Длинный вход явно пропускать по лимиту, не обрезать незаметно.
  Cache при необходимости привязать к hash текста, модели, prompt и config,
  не к SKU; cache hit учитывать отдельно от реального вызова.
- Программные mocks нужны для тестов отказов, но готовность требует хотя бы
  одного настоящего model-run на reviewed dev и реального прохода через общее
  ядро CLI/API. На время первых проб использовать отдельный процесс/config,
  не переключать действующий демо-сервис без разрешённого выпуска. Если опыт
  выполнен только на ВМ, не представлять его как локальный Windows-прогон;
  эксперимент в notebook или пустой адаптер не закрывает R7/замечание ревью.

## 6. Протокол сравнения

### Зафиксировать до изменения правил

База A — rules-only на `5f77d81`, точный code/config SHA, Python/зависимости.
Исторический reviewed-v2 связан с более старым code SHA: R1/R3 меняли identity,
поэтому старую цифру нельзя подписать новым commit без проверки. В разрешённой
реализации получить контрольный прогон в новом каталоге и сопоставить значения,
статусы и evidence с историческими predictions; run_id сравнивать отдельно.
Если поведение различается, сначала объяснить разницу, потом считать Δ.

Варианты B — A + только минимальные проверки; C — B + правила model;
D — C + настоящий LLM fallback. B нужен как абляция, чтобы не приписать
выигрыш от удаления ошибочных кандидатов новому extractor. Для A/B/C достаточно
зафиксированных версий кода; постоянные production-переключатели ради опыта
не обязательны. **C тоже rules-only**, D сравнивать и с A, и с C.

Один неизменный набор входов, schema, gold и evaluator для всех вариантов.
Скрипт сравнения обязан проверить одинаковые SKU/category/group/split и hashes,
дубли, пропавшие и необработанные карточки. Gold не подавать в predict: отдельный
text-only input и отдельный reference для evaluate. Если пришлось исправить
ошибку evaluator, зафиксировать её тестом и пересчитать все варианты.

### Выборки и защита оценки

1. Reviewed-v2 development (10 карточек) — исходный error analysis и подбор
   правил. Сохранить остальные 10 FN как отдельный backlog, не смешивать задачи.
2. Перед итоговым решением расширить development минимум на 20 новых проверенных
   карточек из development-групп: обе категории, отрицательные/конфликтные случаи,
   HTML, неизвестные формы, title-only. Это стартовый объём QA, не статистически
   достаточная выборка. Выбор критериев/seed записать до просмотра предсказаний.
3. После фиксации C выполнить диагностический прогон reviewed-v2 validation.
   Ошибки показать все, включая ухудшения; не называть это независимой оценкой.
   Если по ним меняются правила, явно считать этот набор development-диагностикой.
4. Для независимого итогового сравнения отобрать отдельные reviewed-группы из
   `test_reserved`: проверить пересечения точных и близких дублей/семейств с dev,
   validation и few-shot. Метаданные групп используются только в split/оценке.
   Не открывать этот test для регулярного подбора правил/prompt.
5. Предложение пилота test: минимум 40 карточек, по 20 каждой категории,
   со стратификацией title-only/description и редких форм. Числа требуют ресурса
   ручной проверки и не гарантируют точных оценок по редким атрибутам. При малом
   support публиковать счётчики/N/A; интервалы — только если обоснованы объёмом.
   Отдельный reviewer размечает без predictions и AI-предзаполнения; спорное
   решает второй человек. Если это делает только Влад после нашей AI-разметки,
   честно сохранить статус AI-assisted, не объявлять независимость.

### Что измерять и сохранять

| Измерение | Определение |
| --- | --- |
| Качество | TP/FP/FN, P/R/F1, present/absent/judged support по атрибутам, категориям и category×attribute; micro и macro с явным исключением N/A. Неверное значение = FP+FN. |
| Исключённые пары | ambiguous/unjudgeable отдельно от judged; не увеличивать метрики исключением сложных случаев после просмотра результата. |
| Покрытие | Кандидаты / judged и отдельно / все применимые пары; доля карточек с кандидатом; correct coverage = TP/judged. Все кандидаты review, auto-accepted coverage=0. |
| Δ | Парные переходы A→B→C→D: FN→TP, TP→FP/abstain, новые FP на absent; локальная таблица разбора каждого изменения. Не только общий F1. |
| Срезы | Категория, title-only/description; редкие формы по заранее заданным группам. Продавцы/трафик — N/A без валидных метаданных/семантики, не придумывать веса. |
| Производительность | Одинаковая машина, порядок/объём, concurrency; загрузка модели отдельно, warm p50/p95, end-to-end и throughput, peak RAM/VRAM. Минимум 3 повтора времени, сырой объём и разброс; 10 карточек не дают надёжный p95. |
| Цена D | Вызовы/все карточки и /eligible, successes/timeouts/invalids/cache hits; входные/выходные tokens, включая оплаченные reasoning tokens по usage шлюза, без двойного подсчёта. ₽ = (input_tokens × input_rate + output_tokens × output_rate)/1e6; тариф и дата из панели сохранены. Таймауты/ошибки, синтетические пробы и повторы включать в бюджет, расход сверять с панелью. Для резервного локального backend API-платёж=0, compute N/A без тарифа. |
| Цена A/B/C | LLM calls=0, tokens=0; время CPU измерено отдельно. Не экстраполировать цену D на весь каталог без наблюдаемой доли маршрутизации. |

Новые локальные файлы — в уникальном `outputs/experiments/model-stage/<run>/`:
input/split/reference hashes, variant predictions + штатный manifest,
metrics по split, таблица Δ, latency/cost и experiment manifest. Старые
`outputs/baseline/`, `outputs/evaluation/reviewed-v2/` и frozen gold не менять.
В Git — только исполняемый скрипт сравнения, синтетические fixtures и
агрегированный отчёт без SKU/реальных текстов. Команда создаёт новый run-dir и
останавливается при существующем; повторяемость проверяется отдельным каталогом.
Артефакты читаются через R3 snapshot, без нового механизма записи.

Для rules проверить детерминизм значений/evidence. Для LLM сохранить seed и
decoding, но не обещать побайтовую детерминированность разных backend/hardware;
повторы учитывать в бюджете, выбирать лучший ответ из повторов запрещено.

### Условия остановки и отката

- Любое leakage/выдуманное evidence/неверная роль model → блокировать выпуск,
  исправить причину и добавить synthetic regression, gold не подгонять.
- Новые model FP на проверенном dev или потеря прежних корректных значений
  → остановить расширение правил, сузить опасную конструкцию. Не скрывать FP
  новым фильтром evaluator или исключением карточек.
- C должен сократить FN model без ухудшения наблюдаемой общей precision и
  без необъяснённых изменений других полей. Для D относительно C — добавочные
  TP при отсутствии новых FP на проверенном dev и сохранении прежних TP;
  иначе оставить D экспериментом, не включать default. Малый support прямо указать.
- После фиксации обнаруженная деградация на диагностическом validation
  разбирается явно; любое исправление по нему раскрывается как использование
  набора в разработке. На независимом test правило не подбирается: отрицательный
  результат публикуется; дальнейший подбор требует нового test.
- Превышен согласованный ресурс/timeout/budget либо не подтверждены адрес шлюза,
  идентификатор модели или тариф → остановить model-run. Шлюз недоступен — сохранить rules-only,
  M1/M2 полезны; переход на локальную модель/другой API не делать автоматически.
- Готовые изменения проходят review по смыслу. Прохождение синтетических тестов
  само по себе не разрешает auto_accept или утверждение высокой точности каталога.

## 9. Что требуется от Влада и что можно делать самостоятельно

**До M1:** подтвердить предложенную минимальную нормализацию model и
консервативный отказ при неясной роли кода/границе имени (§3); дать команду
начать реализацию. Уже согласованные 5G, отдельный бренд и конкретные R22/R23
повторно утверждать не нужно. Общую трактовку всех товарных кодов можно пока
не выбирать — спорные случаи останутся abstain.

**До M3:** контур уже выбран организаторами; повторно просить URL, ключ,
список моделей или GPU не нужно. Требуется разрешить выполнение ограниченного
эксперимента на ВМ/в её выданном окружении, утвердить совместимое представление
происхождения модельного ответа/config и предложенный расход до 10 ₽ с учётом
параллельных расходов команды. Согласование плана не означает, что вызовы уже
разрешены/выполнены в этой документационной задаче. Пароли/токены в чат не присылать.

**Для независимой оценки:** договориться о reviewer и времени на закрытый test;
Владу предоставить только конкретные спорные случаи с цитатой и вариантами,
без требования вручную разбирать все 10 324 карточки.

После разрешения M1 самостоятельно можно реализовать бесспорные конструкции,
синтетические проверки, скрипт парного сравнения, dev error analysis и отчёт,
подготовить список спорного и обновить документацию. Это не требует внешнего
API, обучения, изменения VM или расширения контракта. Commit/push/merge и
развёртывание выполняются только в разрешённом объёме следующей задачи.
