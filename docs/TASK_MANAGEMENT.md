# Управление задачами

GitHub Issues — оперативная доска команды. `TASKS.md` — версионируемый индекс,
который показывает, кто и каким commit взял работу. Issue без строки в
`TASKS.md` можно обсуждать, но начинать реализацию по нему нельзя.

## Обязательные labels

У каждой открытой задачи должны быть ровно:

- один `type:*` — область работы;
- один `priority:*` — порядок выполнения;
- один `status:*` — текущее состояние.

Дополнительные labels `risk:*` и `needs:*` используются по необходимости.

### Тип

| Label | Работа |
| --- | --- |
| `type:governance` | правила команды и распределение работы |
| `type:architecture` | контракты, схемы и архитектурные решения |
| `type:data` | ingestion, preprocessing, provenance и split |
| `type:baseline` | правила, словари и deterministic baseline |
| `type:ml` | encoder, обучение и локальный inference |
| `type:llm` | prompts, adapter, structured output и бюджет |
| `type:evaluation` | gold, метрики, эксперименты и анализ ошибок |
| `type:api` | CLI, API и пакетные интерфейсы |
| `type:qa` | тесты, регрессии и сбои |
| `type:ops` | VM, окружение, логи и наблюдаемость |
| `type:docs` | документация и примеры |
| `type:release` | сборка, публикация, manifest и rollback |
| `type:product` | пользовательский сценарий и бизнес-метрики |
| `type:security` | секреты и безопасность данных |

### Приоритет

| Label | Значение |
| --- | --- |
| `priority:p0` | блокирует сдачу, безопасность или основной сценарий |
| `priority:p1` | требуется для ближайшего этапа |
| `priority:p2` | выполняется после основного сценария |
| `priority:p3` | опциональное улучшение |

### Статус

```text
BACKLOG → READY → IN_PROGRESS → REVIEW → DONE
                         ↘ BLOCKED
```

| Label | Условие |
| --- | --- |
| `status:backlog` | результат описан, но зависимости ещё не готовы |
| `status:ready` | есть критерии приёмки и задачу можно брать |
| `status:in-progress` | есть один владелец и опубликованный claim commit |
| `status:blocked` | указан конкретный блокер и следующий шаг |
| `status:review` | открыт PR, проверки приложены, назначен reviewer |
| `status:done` | PR принят, merge выполнен, результат доступен |
| `status:cancelled` | причина отмены записана в Issue |

## Task ID

ID имеет вид `<TYPE>-<NNN>`, например `DATA-002`. Префиксы перечислены в
`TASKS.md`. Номер не переиспользуется после отмены. Один Issue соответствует
одному ID; один PR обычно закрывает один Issue.

## Как взять задачу

1. Выбрать Issue с `status:ready`, проверить зависимости и назначить себя.
2. Создать ветку `<type>/<id>-<slug>` от свежего `work/main`.
3. В `TASKS.md` поставить `IN_PROGRESS`, владельца, ветку, дату и ссылку Issue.
4. Изменить только индекс задачи и сделать commit:
   `chore(tasks): claim <ID>`.
5. Опубликовать ветку: `git push -u work HEAD`.
6. Проверить, что commit виден команде, и заменить label на
   `status:in-progress`.
7. Только после этого менять код, данные, конфигурацию или документы.

Если claim двух исполнителей пересёкся, работу продолжает владелец более
раннего опубликованного commit. Второй исполнитель возвращает свою строку и
выбирает другую задачу.

## Работа, блокировка и передача

- В одном commit должна быть одна понятная причина изменения.
- Новая найденная проблема получает новый Issue и ID, если не входит в scope.
- При блокировке владелец меняет обе доски на `BLOCKED`, пишет причину,
  зависимость и действие для разблокировки, затем публикует commit.
- Перед передачей другому человеку текущий владелец фиксирует состояние,
  незавершённые шаги и последний безопасный commit в Issue.
- Люди и агенты не изменяют общие контракты параллельно без согласованного
  порядка merge.

## Review и завершение

1. Автор обновляет документы и `TASKS.md` до `REVIEW`.
2. PR содержит `Closes #<issue>`, Task ID, claim commit, команды проверки,
   реальные результаты, риски и rollback.
3. Issue получает `status:review` и `needs:review` до назначения reviewer.
4. Reviewer сверяет критерии приёмки, воспроизводимость и границы данных.
5. Интегратор выполняет merge, проверяет GitHub Actions и зеркало Gitea.
6. Интегратор ставит `DONE`/`status:done` и закрывает Issue.

Автор не подтверждает собственную независимую разметку или финальные метрики.
Для security, gold/test, schema и release нужен reviewer соответствующей роли.

## Источники истины

- GitHub Issue: обсуждение, scope, labels и связь с PR;
- `TASKS.md`: владелец, ветка, claim и общий порядок зависимостей;
- PR: изменение и доказательства проверки;
- `docs/PROJECT_STATUS.md`: фактические возможности текущего `main`;
- release manifest: связь GitHub SHA, Gitea SHA, config и артефактов.

Нельзя хранить пароли, API keys, реальные карточки, gold, predictions и полные
логи в Issue, PR или commit. Для подтверждения используются hashes, агрегаты,
synthetic examples и ссылки на разрешённое закрытое хранилище.
