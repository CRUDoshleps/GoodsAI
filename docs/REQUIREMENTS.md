# Требования кейса и состав сдачи

Этот файл связывает исходные требования с текущим кодом. Оригинальный текст
с платформы хранится в
[архиве контекста](product-stage/context/case/platform-requirements.md).

Сверка реализации: **20.10.2026, код `1c64463`**. Это дата аудита, не обещание
качества всех категорий. Версии измерений и reference отдельно указаны в
[RESULTS](RESULTS.md); источник конкретной публикации Gitea — submission-manifest.

20.10.2026 по скриншотам разделов 2–6 и уточнению Владислава принята
[политика SPEC-001](../TECHNICAL_SPEC.md#0-действующая-политика-команды--spec-001),
`spec-team-v1`: отделены требования кейса, действующий контракт команды и
незакрытые условия. Нового ответа организаторов или изменения runtime нет.

## Задача

Автоматически извлекать из текста карточки бренд, модель и обязательные
категорийные характеристики, нормализовать значения и возвращать confidence.
Нужно учитывать качество, стоимость, длинный хвост, редкие значения и
возможность ручной проверки. Изображения не используются.

## Ограничения

| Требование | Реализация сейчас | Долг |
| --- | --- | --- |
| text-only, включая атрибуты продавца по ТЗ | `Product.from_dict`: title/description/category; непустые seller attributes отклоняются в E1 | DATA-002: доказать seller provenance и реализовать источник/evidence; это ограничение E1, не запрет кейса |
| структурированный выход | одинаковый JSONL/JSON schema `0.1` для CLI/API | официальный окончательный HTTP/batch контракт |
| значение подтверждается текстом | общий CandidateVerifier для rules/LLM/cache/experimental GLiNER: exact raw/visible evidence, типы, единицы, роль памяти, границы модели, отрицания/совместимость/чужие сущности | семантические проверки консервативны; не гарантируют понимание любого текста |
| нормализация | source выдаёт canonical Candidate; общий gate сверяет с evidence, aliases, units и configured bounds | приёмка новых категорий и согласованный mapping |
| confidence и порог надёжности по ТЗ | heuristic score, все значения только `review`, неопределённость — `abstain` | независимая калибровка и обоснованный порог не выполнены; `auto_accept` запрещён |
| несколько категорий | default: смартфоны `761` и чайники `482`; opt-in train-only registry config v2 уже реализован | реальные новые категории/ноутбуки не приняты; synthetic 30-category test не равен качеству каталога |
| ML/LLM в pipeline | интегрированный opt-in LLM fallback в общей сборке CLI/API; отдельный экспериментальный GLiNER для однословного бренда | сравнительная польза актуальных методов на общем reference и независимая оценка |
| стоимость и отказы LLM | calls/physical attempts/tokens/cache/failures, pricing при заданных ценах, ledger, concurrency, deadline и byte limit | стоимость без цен N/A; compute не считается бесплатным; фактический benchmark отдельно |
| ручная проверка | `review`, reasons/evidence; отдельная консоль brands/colors с versioning/RBAC/rollback и утилита приоритета | это не законченная общая очередь подтверждения атрибутов #19/#50 и не human UX benchmark |

Проверяемые точки входа: [QUICKSTART](QUICKSTART.md), [VERIFIER](VERIFIER.md),
[LLM](LLM.md), [ARCHITECTURE](ARCHITECTURE.md), [RESPONSES](RESPONSES.md).
Default rules работает без model API. Synthetic acceptance проверяет внешний
JSONL и HTTP без packaged examples; качество каталога из этого PASS не следует.

## Категорийные поля

В исходном описании явно названы для смартфона бренд, модель, объём памяти,
диагональ, батарея и цвет. Текущая схема дополнительно разделяет `ram_gb` и
`storage_gb`; это зафиксированное решение команды `spec-team-v1`, не отдельный
официальный перечень. Обязательность поля не означает, что отсутствующее в
тексте значение нужно заполнить догадкой.

Для ноутбука названы бренд, процессор, RAM, накопитель, диагональ и цвет.
Ноутбуки default-профилем не поддерживаются; реальный registry-пилот ещё не принят.
Схема чайника выбрана командой по
исследованию данных и не выдаётся за официальный список кейса.

## Шесть обязательных артефактов

| № | Артефакт | Сейчас | Закрывающая задача |
| --- | --- | --- | --- |
| 1 | воспроизводимый код/ноутбук | код, CLI/API, synthetic tests, locked clean-run | независимая приёмка выбранного SHA на целевой VM |
| 2 | README | внешний JSONL, ожидаемый output, API и проверка артефактов | повторить на финальном окружении/профиле |
| 3 | EDA | код, агрегаты и датированный checkpoint | актуальные source/data manifests для финального набора |
| 4 | pipeline extraction | rules end-to-end; опциональный LLM с общим gate, schema и ограниченным provider | измеренный выбор гибрида и новых категорий |
| 5 | predictions по карточкам | private development batch; ART-003 связывает predictions/metrics/config/EDA/report hashes | финальный согласованный набор и канал передачи реального файла |
| 6 | финальная презентация | продуктовая и техническая checkpoint-версия 19.10 | выводы и метрики окончательного candidate |

Файл predictions считается готовым только вместе с входным hash, Git SHA,
конфигом, количеством строк и metrics report. Агрегат не заменяет сам файл.
Offline-инструмент [ART-003](ARTIFACT_BUNDLE.md) связывает эти файлы в manifest,
проверяет input/predictions и показывает missing/incomplete. Smoke с шестью
синтетическими входами не считается всем каталогом или финальным комплектом.

## Автоматическая техническая оценка

Организаторы проверяют последний commit `main` в Gitea и работающий сервис на
выданной VM. Для текущего этапа приложение должно слушать `0.0.0.0:8000`.
Точный API может быть уточнён организаторами; временный `/predict` не объявляется
окончательным контрактом.

| стоимость | LLMShare, tokens и рубли на 1 000 SKU |

## Решения при отсутствии дополнительных разъяснений

Владислав 20.10.2026 подтвердил отсутствие дополнительных сведений. SPEC-001
фиксирует рабочие решения; получение ответа организаторов не заявляется.

| Пункт | Действующее решение | Что остаётся открытым |
| --- | --- | --- |
| поля категорий | смартфон/ноутбук — примеры из ТЗ, схема E1 и RAM/storage — командная | остальные категории и точный официальный перечень; реальное покрытие проверяется отдельно |
| batch/confidence/отказ | JSONL v0.1, общий с HTTP объект результата; heuristic, review/abstain | калибровка и threshold; официальный иной wire format потребует адаптера |
| seller inputs | по ТЗ разрешены исходные seller attributes; в E1 не реализованы | DATA-001/DATA-002: доказательство происхождения колонок и совместимая форма evidence |
| конфликты/нормализация | P04–P11 в TECHNICAL_SPEC, прежние согласованные правила | новые aliases и спорные catalog equivalence требуют отдельного решения |
| HTTP | текущие /predict, /health, /docs; порт 8000 | окончательные endpoints/транзакции неизвестны, временный контракт не выдаётся за официальный |
| LLM gateway | реальные данные не отправляются без явного scope/hash/model/budget решения команды | разрешение конкретного пакета и ограничения владельца данных; test reserve закрыт |
| передача predictions | подготовка закрытого локального release-комплекта, в Git только безопасный публичный состав | канал/получатель и допустимость передачи полного комплекта должны быть определены до финальной сдачи |
| трафик | отдельная offline-оценка только по разрешённым данным с provenance | при отсутствии согласованных weights — N/A; clicks не являются входом extractor |

Эти решения позволяют начать матрицу подтверждённых сценариев SPEC-002;
seller inputs, новые категории, независимое качество и полный release не
объявляются реализованными только из-за фиксации политики.
