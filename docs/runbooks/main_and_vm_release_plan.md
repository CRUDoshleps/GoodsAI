## Порядок работ и критерии готовности

| Приоритет | Этап | Действия | Что считается результатом |
| --- | --- | --- | --- |
| P0, первым | Опубликовать текущий baseline в main | Проверки, документационный commit, feature push, PR/merge в main | Remote main действительно содержит baseline, свежие отчёты и инструкцию |
| P0 | Воспроизвести тот же код на ВМ | Проверить среду/репозиторий/данные, установить окружение, выполнить тесты и CLI smoke | Записаны commit SHA, команды, версии и фактический JSON-результат |
| P0 на выходные | Сервис на порту 8000 | Тонкий временный адаптер над extractor; официальный API позже | Проверены процесс, health/predict и доступ с нужной стороны |
| P0 после выдачи спецификации | Адаптировать официальный контракт | Сопоставить endpoint'ы, payload, транзакции, auth и отказы | Пройдены контрактные проверки, доступность проверена требуемым способом |
| Далее | Улучшать качество | Model, цвета/бренды/числа, затем ML или LLM | Отдельные изменения с измерениями на фиксированном reference |

Не ждать готовности сервиса или новой модели, чтобы сделать первый пригодный
для code-review main. Публикация текущего решения — отдельная ранняя контрольная
точка. Для первой проверки ориентир: **main готов до 06:00 МСК 18 октября**;
оставить запас на авторизацию и merge. Рабочая цель 05:00 — наш запас,
не дополнительный срок организаторов. Если времени недостаточно, сначала
интегрировать уже работающий CLI и честно обозначить статус ВМ/API.

## A. Выпуск в Gitea main

1. Восстановить локальную авторизацию Git через Credential Manager/интерфейс.
   Пароли/токены не размещать в URL remote, shell-командах, файлах или логах.
   После успешного fetch сравнить main/feature и посмотреть новые коммиты
   других участников; не строить merge по устаревшему `origin/main`.
2. Проверить diff и публикуемые документы: актуальная оценка — reviewed-v2,
   статус реализации отделён от планов. В корневом README сделать понятный
   вход для проверяющего: назначение, установка, синтетический пример запуска,
   тесты, ограничения, ссылки на EDA/метрики и запуск ВМ. Пример не должен
   требовать локальных реальных датасетов, которых нет в Git.
3. Проверить `.gitignore`, tracked/staged состав, секреты и большие бинарные
   файлы. Только выборочный `git add` по проверенным путям; совет организаторов
   `git add -A` не применять вслепую к этой рабочей копии с локальными данными.
4. Сохранить локальные отчёты отдельным commit в feature. Push feature не
   завершает задачу: проверить/обновить существующий PR #2 либо создать PR,
   если после проверки его уже нет. Конфликты разрешать с сохранением чужой работы.
5. После review и разрешённого слияния в **main** проверить через fetch/remote,
   что main содержит baseline и новый commit. Не использовать force-push,
   reset/clean или замену истории main. Разрешение на план не равно выполненному merge.
6. В интерфейсе Gitea открыть именно main: видны `src/goodsai`, tests,
   pyproject, README, EDA и актуальные отчёты. На платформе отдельно проверить
   «Последний push в Gitea». Записать SHA интегрированного main; branch name
   feature или наличие PR не являются доказательством публикации в main.

## B. Проверка и запуск ВМ

1. Получить SSH alias либо host/port/user и способ авторизации. Ключ остаётся
   локально, пароль вводится в клиенте. Если используется Jupyter-terminal,
   те же действия выполняются в нём. Ни адреса доступа, ни секреты не входят
   в публичный runbook. Подключение/изменения выполняются следующим согласованным этапом.
2. Сначала read-only инвентаризация: OS, CPU/RAM/disk, Python, текущий пользователь,
   `~/project`, remote/branch/status, существующие процессы, занятые порты и
   расположение данных. Не перетирать локальную работу участников или данные.
3. При чистом совместимом checkout получить проверенный main и зафиксировать
   **тот же SHA**, что опубликован в A. При изменениях/расхождении истории сначала
   сохранить и разобраться с ними; не выполнять принудительный reset/clean.
4. Установить окружение с Python >=3.12 по README. Проверить доступность wheel
   PyArrow и ограничения сети. Если Python не подходит, выбрать доступное
   совместимое окружение после осмотра; не менять системный Python вслепую.
5. Выполнить тесты и CLI на небольшом синтетическом входе: смартфон, чайник,
   конфликт, неизвестная категория, невалидная запись. Проверить JSON, spans,
   явные отказы. Для этого не нужны pickle, full EDA или реальные карточки.
6. Проверить наличие официальных данных. Для реального smoke достаточно
   разрешённого небольшого входа/существующего E1, с проверкой hashes;
   не копировать 2.39 ГиБ raw без необходимости. Данные передаются отдельно,
   не добавляются в main. Полный реальный запуск и итоговый файл predictions
   остаются отдельным артефактом сдачи, не заменяются синтетическим примером.
7. Для HTTP-сервиса из C проверить запуск, состояние процесса, запрос с ВМ,
   предусмотренную платформой внешнюю доступность и повторный запуск. Закрыть
   SSH и проверить, что сервис продолжает отвечать. Один успешный CLI-вызов
   подтверждает выполнение, но ещё не готовность endpoint-сервиса.
8. Сохранить проверенный протокол `docs/runbooks/vm_reproduction.md`:
   commit SHA, окружение, команды/exit codes, тесты, smoke и ограничения.
   Общие результаты — в Git, реальные ответы/логи с данными — локально.

## C. Временный HTTP-адаптер на 8000

Варианты и принятое решение после уточнения администраторов:

- **CLI на ВМ первым шагом**: минимальные изменения, быстро подтверждает
  совместимость. Закрывает воспроизводимость, но не доказывает готовность
  будущего сетевого/транзакционного контракта.
- **Выбран тонкий Python HTTP-адаптер над существующим ядром**:
  проверка состояния и извлечение из JSON; логика правил не дублируется,
  официальный контракт позже заменяет только внешний адаптер. Добавляет
  зависимость сервера, тесты границы и управление процессом, но не новый ML pipeline.

Имена и формат временных endpoint'ов — внутренняя договорённость команды,
не спецификация организаторов. Реализация: FastAPI/Uvicorn, `/`, `/health`,
`/predict` поверх текущего Product/prediction v0.1; инструкции и ограничения
в [runbook сервиса](http_service.md). Порт ВМ 8000; менеджер процесса выбирается
после диагностики. Использован Python stack существующего проекта; отдельный Java-сервис,
БД, очередь, frontend и Docker для этого этапа не требуются.

Для сервиса предусмотреть строгий вход, ограничение размера запроса, JSON-ошибки,
те же evidence/отказы, управляемую конфигурацию и smoke без датасета. Ошибочные
запросы не должны превращаться в успешный пустой ответ. Не публиковать реальные
карточки в логах. Не подключать paid/external LLM, не менять confidence.

Способ автозапуска выбрать после осмотра ВМ: существующий менеджер процессов
или доступный systemd/user-service. Запуск в foreground Jupyter/SSH не выдавать
за устойчивый deployment. Не менять firewall/публичные порты и auth вслепую:
сначала выяснить механизм доступа и требования платформы.

После выдачи endpoint'ов проверить методы/пути, request/response schema,
синхронность/пакеты/транзакции, auth, таймауты/лимиты, путь health и доступность
с проверяющей стороны. До этого нельзя утверждать совместимость с функциональным
автотестом. Репозиторный LLM-review и проверка живого сервиса — разные подтверждения.

## Ежедневный цикл

Изменения в feature → относящиеся tests → публикация/merge main до окна →
проверка SHA remote и строки платформы → обновление ВМ тем же SHA → smoke →
изучение результата прогона. На время запрета push можно работать локально;
отправлять после уведомления о завершении. Не обходить блокировку.

При проблеме нового deployment вернуть сервис к предыдущему проверенному
release/окружению без переписывания Git-истории; исправления публиковать новым
commit. Прошлый работавший SHA хранить в протоколе, данные не удалять.
