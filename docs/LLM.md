# LLM-003: evidence-first LLM fallback

Реализация интегрирована в main; аудит кода **20.10.2026 на `1c64463`**.
Исходная интеграция — PR #90 (`62898fb`), validation/bounded provider и общий
gate приняты последующими PR. [LLM-003 #25](https://github.com/CRUDoshleps/GoodsAI/issues/25)
остаётся открытой по своей приёмке; статус issue не означает отсутствия кода.
CLI/API создают маршрут через `composition.build_runtime`. В CLI нужен `--llm`,
в API — `GOODSAI_LLM_ENABLED=1`; без явного включения работают rules,
`llm_calls=0`. Наличие маршрута не подтверждает его сравнительную пользу.

## Что делает

Правила всегда запускаются первыми. Модель вызывается не на каждую карточку:

1. Карточка, где правила нашли все атрибуты схемы, в LLM не идёт.
2. Найденные правилами значения и конфликты (`conflicting_evidence`) модели не
   передаются и не перезаписываются.
3. Из пропусков `not_found_by_rules` дешёвый pre-router (`has_signal`, только
   regex по видимому тексту) оставляет те, которые verifier вообще может принять:
   число с подходящей единицей для числовых полей, слово из справочника цветов
   для цвета, небрендовое слово в title для бренда и модели. Остальные получают
   `llm_skipped_no_signal` и не попадают в запрос.
4. Если после этого пропусков не осталось — вызова нет. Иначе один запрос на
   карточку со всеми оставшимися атрибутами.
5. Дальше — кэш точных запросов и жёсткий бюджет вызовов на запуск.

Pre-router не меняет набор принимаемых значений: всё, что он отсекает, verifier
отклонил бы после вызова. На 8 синтетических карточках репозитория из 27
пропусков в запрос попали 8, вызовов — 5 из 8 карточек; доля на реальном
каталоге не измерена.

В quote-режиме по умолчанию (span selector выключен) ответ модели — предложение,
а не результат. Значение принимается, только если:

1. ответ — JSON-объект `{"attributes":[{"attribute","value","quote"}]}` без
   других ключей;
2. атрибут был запрошен у модели;
3. `quote` дословно (с точностью до пробелов) есть в видимом тексте title или
   description;
4. значение выводится из цитаты тем же нормализатором, что у правил: число с
   единицей внутри цитаты (`5000 мА*ч` → `5000`, `500 мл` → `0.5`), цвет из
   справочника, бренд или модель как слово из цитаты;
5. перед значением нет признаков диапазона или отрицания (`до`, `от`, `не`,
   `без`), а бренд не стоит после `для` / `совместим`;
6. кандидат проходит общий `CandidateVerifier` (структура, нормализация,
   evidence, роли/отрицания/совместимость), а строка — `validate_prediction`.

Принятое значение получает `method="llm"`, `decision="review"`,
`confidence_kind="heuristic"`, `confidence=0.6` и `rule_id="llm.llm-fill-v1"`.
`auto_accept` этот маршрут не создаёт. Score не является вероятностью.

Если модель предложила разные допустимые значения одного атрибута, итог —
`abstain` с `conflicting_llm_evidence`.

### Повреждённый ответ и кэш (LLM-007)

Перед поиском атрибута в схеме проверяется структура каждого предложения:
ровно `attribute`, `value`, `quote`; имя — непустая строка, значение — строка
или конечное число (не boolean), цитата — строка. Явный отказ `value=null`
разрешает `quote=null` или строку. Массивы/объекты вместо полей отвергаются
с `llm_bad_types`, неверный набор ключей/элемент — с `llm_unknown_field`.
Эти проверки одинаковы для свежего ответа, replay кэша и входа в grounding.

Смешанный ответ обрабатывается по предложениям: ошибочный элемент не отменяет
другой корректный кандидат, прошедший grounding/verifier. Одинаковые допустимые
дубликаты дают один кандидат; разные допустимые значения сохраняют конфликт.
Неизвестные и уже решённые правилами атрибуты игнорируются со счётчиком
`llm_unknown_attribute`. Поля rules не перезаписываются.

У оставшегося пропуска сохраняется `abstain`: сначала его собственная причина
отказа, иначе первая структурная ошибка без распознаваемого запрошенного имени,
иначе `llm_not_found`. Коды фиксированы и не содержат содержимого ответа.
Повторяющиеся JSON-ключи отвергаются целиком, без выбора последнего значения.
Неверный JSON/envelope кэша считается miss; список proposals из читаемой записи
проверяется поэлементно, без вызова провайдера.

Gateway envelope проверяется до учёта usage: `choices` — непустой массив,
первый `message` — объект с текстовым `content`. `usage` можно опустить или
передать `null`; указанные счётчики — только целые неотрицательные числа без
преобразования строк/boolean/float. `model` можно опустить или передать `null`,
иначе нужна строка до 200 символов. Неверный envelope/метаданные дают
`llm_malformed_response`, неверная JSON-структура content — `llm_malformed_json`.
Повторной попытки из-за этих ошибок нет; успешные поля rules сохраняются.

Предел bytes ответа, общий deadline и учёт физических retries остаются
[LLM-008 #100](https://github.com/CRUDoshleps/GoodsAI/issues/100).
Проверка структуры не заменяет эти ограничения и не доказывает качество LLM.

## Запуск

Endpoint и ключ берутся только из окружения. Модель, timeout, retries, бюджеты,
цены и остальные настройки разрешаются единым resolver CLI/API: `runtime.llm`
профиля → разрешённые env → явные CLI-флаги. Полная таблица, fail-fast и
production-пример — [CONFIGURATION](CONFIGURATION.md#conf-002-единый-resolver-и-production-пример).
Шаблон env — [`.env.example`](../.env.example); реальный `.env` в Git не попадает.

```bash
export GOODSAI_LLM_BASE_URL=<OpenAI-совместимый base URL шлюза, с /v1>
export GOODSAI_LLM_API_KEY=<ключ>
export GOODSAI_LLM_MODEL=<имя модели шлюза>

.venv/bin/python -m goodsai.cli predict \
  --input <внешний>.jsonl --output outputs/llm-run/predictions.jsonl \
  --llm --llm-max-calls 100 --llm-cache-dir outputs/llm-cache
```

Первый живой вызов — одна синтетическая карточка, придуманная для проверки
(не из каталога). Команда пишет trace с моделью, предложением, результатом
verifier и фактическим usage и завершается с кодом 3, если вызов не удался:

```bash
.venv/bin/python -m goodsai.cli llm-trace --output outputs/llm-trace/trace.json
```

| Флаг | По умолчанию | Назначение |
| --- | --- | --- |
| `--llm` | выключен | включить маршрут |
| `--llm-model` | профиль, затем `GOODSAI_LLM_MODEL` | имя модели; при opt-in без него запуск завершается с кодом 2 |
| `--llm-max-calls` | 100 | бюджет логических provider operations за запуск |
| `--llm-daily-max-calls` | 300 | общий дневной бюджет по журналу |
| `--llm-budget-file` | `outputs/llm-budget/ledger.json` | журнал дневного бюджета |

| `--llm-attempts` | 3 | попыток на запрос вместе с повторами (1–5) |
| `--llm-concurrency` | 2 | одновременных запросов к шлюзу |
| `--llm-max-tokens` | 2048 | запрашиваемый лимит output tokens |
| `--llm-circuit-breaker` | 5 | отключение после последовательных отказов |

HTTP API: `GOODSAI_LLM_ENABLED=1`, `GOODSAI_LLM_MODEL`,
`GOODSAI_LLM_MAX_CALLS` (по умолчанию 100), `GOODSAI_LLM_DAILY_MAX_CALLS` (300),
`GOODSAI_LLM_BUDGET_FILE` плюс те же переменные endpoint и
ключа. `/health` тогда показывает модель, число вызовов, cache hits и причину
отключения, без URL и ключа. `run_id` ответа — `http-rules-llm-v0`.
API теперь применяет также timeout/retries/concurrency/token limit/cache/prices
из того же профиля/env, что CLI, без отдельного набора defaults. `/health`
показывает `runtime_policy_sha256` и `effective_config_sha256`; полная применённая
политика есть в batch manifest. Профиль сам LLM не включает, CLI требует `--llm`.

`--llm-json-mode` только просит шлюз о JSON. Это не constrained decoding:
структура всегда проверяется на клиенте. Поддержку `response_format` у шлюза
хакатона нужно проверить отдельно.

## Отказы и причины

Сбой провайдера не меняет решений правил. Запрошенные атрибуты остаются
`abstain`, к `not_found_by_rules` добавляется одна причина:

| Причина | Когда | Повтор |
| --- | --- | --- |
| `llm_missing_key` | нет base URL или ключа | нет, маршрут отключается до конца запуска; запрос не отправлялся, `calls` не растёт |
| `llm_auth_failed` | HTTP 401/403 | нет, маршрут отключается |
| `llm_rate_limited` | HTTP 429 после всех попыток | да, учитывается `Retry-After` (не больше 30 с) |
| `llm_server_error` | HTTP 5xx после всех попыток | да, пауза 1, 2, 4 с |
| `llm_timeout`, `llm_network_error` | timeout или сеть после всех попыток | да |
| `llm_http_error` | прочие HTTP 4xx | нет |
| `llm_malformed_response` / `llm_malformed_json` | ответ шлюза или модели не по схеме | нет |
| `llm_budget_exhausted` | исчерпан `--llm-max-calls` | вызов не выполняется |
| `llm_daily_budget_exhausted` | исчерпан дневной лимит журнала | вызов не выполняется |
| `llm_budget_ledger_unavailable` | журнал не читается или испорчен | нет, маршрут отключается |
| `llm_endpoint_not_allowed` | URL не HTTPS или содержит учётные данные | нет, маршрут отключается |
| `llm_blocked_by_data_policy` | карточка помечена как закрытый test | вызов не выполняется |
| `llm_circuit_open` | 5 неудачных вызовов подряд | маршрут отключается до конца запуска |
| `llm_deadline_exceeded` | истёк общий дедлайн запроса (очередь, попытки, паузы) | нет; если ничего не отправлено, логический вызов не списывается |
| `llm_response_too_large` | тело ответа больше лимита (по Content-Length или по факту чтения) | нет |
| `llm_too_many_proposals` | модель вернула больше предложений, чем `max_proposals` | нет |

Отклонённые предложения модели дают причину на атрибуте и счётчик в manifest:
`llm_quote_not_found`, `llm_value_not_in_quote`, `llm_value_not_in_schema`,
`llm_uncertain_context`, `llm_foreign_entity`, `llm_span_not_visible`,
`llm_failed_verification`, `llm_bad_types`, `llm_unknown_field`;
`llm_unknown_attribute` — только счётчик. Если модель ничего не нашла —
`llm_not_found`.

Тексты исключений провайдера, тело запроса и ответа в логи и manifest не
пишутся. После запуска с отключённым маршрутом CLI печатает в stderr одну строку
с причиной.

## Учёт в manifest

При `--llm` manifest получает `method_counts` и объект `llm`: модель, версия
промпта, лимиты, `cards_routed`, `cards_without_gap`, `cards_skipped_no_signal`,
`attributes_skipped_no_signal`, `calls`, `retries`, `cache_hits`, токены,
`cost` и `cost_status`, `accepted` по атрибутам, `rejected`, `failures`,
`disabled_reason`, время провайдера. Поле `llm_calls` считает логические операции
провайдера; cache hit не считается. Одна операция может сделать несколько
физических HTTP-попыток: их число — `attempts`, повторы — `retries`. Дневной
журнал считает именно `attempts`. Если запрос не отправлен совсем (дедлайн в
очереди, отказ журнала), `calls` не увеличивается.
Настройки маршрута входят в `run_id`, поэтому
rules-only и LLM-запуски на одном входе различаются.
CONF-002 дополнительно сохраняет effective profile/policy и два hashes без
endpoint/key; изменение цен/timeout отражено в provenance. Старые результаты
не перезаписываются.

## Кэш

`--llm-cache-dir` хранит разобранные предложения модели под ключом SHA-256 от
полного запроса: сообщения, модель, версия промпта, параметры генерации и hash
конфигурации. Любое изменение текста, схемы, промпта или модели — промах.
Попадание в кэш снова проходит все проверки из раздела «Что делает»;
испорченная запись считается промахом. Записи содержат цитаты из карточек,
поэтому каталог кэша должен лежать вне Git (например, `outputs/`).

Объединение одновременных одинаковых запросов, TTL, namespace/revision,
integrity и аудит доли повторов реализованы в main (PR #128). Они явно
настраиваются и описаны в [EXACT_CACHE](EXACT_CACHE.md). Репрезентативное
решение keep/drop для cache остаётся отдельной экспериментальной приёмкой.

## LLM-008: ограничения вызова

`[DONE]` в ветке `llm/llm-008-bounded-calls`, задача
[LLM-008 #100](https://github.com/CRUDoshleps/GoodsAI/issues/100).

- Тело ответа читается кусками и не больше `max_response_bytes + 1` байт;
  Content-Length — только ранняя подсказка, отсутствующий или ложный заголовок
  и chunked/close-delimited ответы ловятся по факту чтения.
- Один дедлайн на логический запрос карточки покрывает ожидание слота
  concurrency, каждую попытку, паузы между ними и socket timeout: timeout каждой
  попытки — `min(timeout_seconds, остаток)`, пауза, пересекающая дедлайн, не
  делается.
- Перед каждой физической попыткой резервируется место в дневном журнале.
