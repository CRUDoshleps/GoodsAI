## Что уже есть

Работает Python CLI для смартфонов (`761`) и чайников (`482`), есть правила,
нормализация, текстовые подтверждения и тесты. `model` пока не извлекается.
Подготовлены 120 AI-размеченных карточек; на 22 полных пользовательских проверках
выполнена [оценка baseline reviewed-v2](research/baseline_evaluation_v2.md).
Validation: 12 карточек / 67 judged-пар, P=96,7%, R=58,0%, F1=72,5%; независимых
gold/test-метрик ещё нет, результат не относится ко всем 120 карточкам.
Linux-запуск пока не подтверждён. Состояние проекта и ограничения:
[PROJECT_STATUS.md](PROJECT_STATUS.md).

**База для новой работы — актуальный `origin/main` после fetch.** Baseline,
исследования и текущие отчёты интегрированы через PR #2 (`b3b3d55`, 17 октября).
Каждый создаёт свою ветку от согласованного commit main и фиксирует SHA.
Ранее рекомендованная feature-база больше не нужна; до fetch main на ВМ
может всё ещё указывать на начальную настройку.

## T1. Участник A: воспроизводимость Linux-запуска

**Начать с:** [AGENTS.md](../AGENTS.md), [baseline.md](baseline.md),
[pyproject.toml](../pyproject.toml), разделов 8–9 статуса проекта.

Что сделать:

1. В отдельной рабочей копии взять согласованный commit из Gitea. Указать его
   SHA в отчёте. Не считать локальные незакоммиченные файлы Влада доступными команде.
2. На доступном Linux/WSL создать чистое Python-окружение, установить проект
   по инструкции и запустить существующие тесты. Зафиксировать версии ОС,
   Python и зависимостей, команды и exit codes.
3. Проверить `predict` на небольшом **синтетическом** JSONL: смартфон, чайник,
   неизвестная категория, невалидная запись. Проверить формат результата,
   evidence и поведение при ошибках, ориентируясь на действующий контракт.
4. Если официальные данные уже доступны локально, отдельно воспроизвести
   подготовку и прогноз. Не повторять полный EDA; использовать существующую
   инструкцию получения доверенной проекции. Результаты писать в свой каталог
   `outputs/`, не перезаписывать чужие файлы.
5. Описать фактический запуск, проблемы и минимальные необходимые исправления.
   Запуск на VM организаторов — отдельный этап после согласования доступа;
   успешный WSL-прогон не выдавать за проверку VM.

**Результат:** `docs/runbooks/linux_reproduction.md`; при необходимости —
минимальное исправление установки/совместимости в отдельном изменении.
Не добавлять сервер, БД, Docker или CI только ради этой задачи.

**Готово, когда:** установка и синтетический CLI-прогон воспроизведены на Linux,
относящиеся тесты проходят, указаны среда/commit/команды. Если данных нет,
реальный data-run честно помечен как непроверенный, а проверка окружения завершена.
Секреты, реальные карточки и полные логи в Git не включать.

## T2. Участник B: прототип извлечения модели товара

**Проблема:** текущий baseline всегда возвращает отказ для атрибута `model`.
Можно подготовить консервативный прототип, пока Влад проверяет разметку.

**Начать с:** [контракта](research/architecture_and_contract.md),
[rules.py](../src/goodsai/rules.py), [text.py](../src/goodsai/text.py),
[verify.py](../src/goodsai/verify.py), [плана разметки](research/annotation_plan.md).

Что сделать:

1. Реализовать изолированный прототип для явно написанного коммерческого имени
   или кода модели в названии; использовать описание только при достаточном
   контексте принадлежности этому товару.
2. Не включать в `model` бренд, память, цвет и состояние товара. Дополнительные
   коды, серии и неоднозначные границы обрабатывать консервативно, с отказом
   при отсутствии согласованного правила.
3. Сохранять точный raw span, включая корректное сопоставление HTML/entities.
   Ориентироваться на существующий `Candidate`, не менять публичный JSON-контракт.
4. Проверить на синтетических примерах: явная модель; название без модели;
   повтор бренда; память/цвет рядом; несколько кодов; модель другого товара
   в описании; разрыв HTML-тегами. Отдельно показать ожидаемые отказы.
5. При наличии локальных данных исследовать только development. Не подбирать
   правила по `review24.md`, validation-ответам или test_reserved, не использовать
   готовое поле `model` каталога как ответ или lookup по SKU.

**Рабочая область:** новые `scripts/research/prototype_model_rules.py`,
`scripts/research/test_model_prototype.py`, `docs/research/model_prototype.md`.
Это предлагаемые новые файлы. Общие `rules.py`, `baseline.json`, `verify.py`
пока оставить интегратору: прототип должен проверяться отдельно.

**Готово, когда:** есть запускаемый прототип, осмысленные синтетические проверки,
точные spans, описанные отказы и список решений для интеграции. Более широкое
покрытие само по себе не считать доказательством улучшения precision/F1.
Интеграция и замер качества — после фиксации инструкции и reference.

## T3. Участник C: аудит дублей и разделения данных

**Начать с:** [evaluation.md](research/evaluation.md),
[annotation.py](../src/goodsai/annotation.py),
[test_data_and_annotation.py](../tests/test_data_and_annotation.py).

Что сделать:

1. Проверить локальные `data/gold/e1/split_manifest.jsonl` и
   `data/processed/e1/pilot.jsonl`: уникальность SKU, полноту соответствия,
   отсутствие пересечения групп между development/validation/test_reserved.
2. Проверить точные и нормализованные дубли названий/описаний между split.
   Для близких дублей предложить воспроизводимый критерий и выдать кандидатов
   на проверку; не объявлять все похожие короткие названия одинаковым товаром.
3. Для test_reserved ограничиться аудитом идентификаторов, групп и текстовых
   fingerprints; не использовать его примеры для настройки извлечения.
4. Сохранить подробные пары SKU/тексты только локально в `outputs/`.
   В командный отчёт вынести метод, агрегаты, ограничения и рекомендации.
5. Не менять split-manifest, исходные tasks и разметку. Если найдена утечка,
   передать список Владу: изменение split требует отдельной версии набора.

**Результат:** новые `scripts/research/audit_splits.py`,
`scripts/research/test_split_audit.py`, `docs/research/split_audit.md`.
В тестах — синтетические дубли/недубли и известный пример межsplit-пересечения.

**Готово, когда:** есть воспроизводимый отчёт с количеством проверенных записей,
разделением подтверждённых нарушений и кандидатов, а также hashes входов.
Если данных пока нет, сначала подготовить скрипт и синтетическую проверку;
реальный аудит пометить как ожидающий данных.

## T4. Участник C: требования к сдаче и вопросы организаторам

Можно выполнить параллельно T3 без доступа к датасетам. Свериться с
[актуальным разбором задания и состава сдачи](REQUIREMENTS_AND_DELIVERY.md)
и [требованиями платформы](product-stage/context/case/platform-requirements.md).
Продуктовая таблица соответствия содержит проектные намерения, не отчёт о
готовых компонентах и не дополнительные обязательства организаторов.

Подготовить `docs/research/open_questions.md` с вопросами:

- Где полная категорийная схема и справочники значений? Примеры обязательных
  полей смартфона/ноутбука уже есть в задании; точный перечень обещан с данными.
- Каковы формат входа/выхода, единицы, шкала confidence и допустимость отказа?
- Есть ли приоритет title/description при конфликте? Допустимы ли составные цвета
  и восстановление пропущенных единиц памяти? Как оцениваются ошибки исходника?
- Каковы точные время/канал сдачи и требования запуска на VM? Шесть артефактов
  и формат «один репозиторий или архив, запуск по README» уже определены.
  Уточнить схему predictions и передачу файла при исключении результатов из Git.
- Есть ли отдельная выдача размеченной части train/validation и нормативной
  схемы, обещанных в разделе 6, но не найденных в исследованных файлах?
- Если нужен LLM-эксперимент: какие модели/gateway разрешены, каковы лимиты,
  бюджет и правила передачи данных?

**Готово, когда:** подтверждённые требования отделены от открытых вопросов;
для каждого ответа указан документ/ссылка/дата. Черновик вопросов передать
координатору команды. Сам документ не означает, что организаторам уже написали.
Не ждать ответов, чтобы завершить подготовку списка.

## После завершения проверки разметки

Влад фиксирует версию инструкции и указывает, какие карточки/атрибуты реально
проверены человеком. Затем участник C запускает оценку на допустимой проверенной
validation-части и делает error analysis; участник B готовит интеграцию прототипа;
участник A повторяет итоговый запуск на согласованной целевой среде.

После раунда 5 есть 22 полных проверки: 10 development и 12 validation
(`review.human-reviewed.v6.jsonl`, только локально). В reviewed-v2 из 130 пар
исключены 5 ambiguous и 1 unjudgeable; контекстные гипотезы хранятся отдельно.
Участнику C остаются независимая перепроверка расчётов/меток и полный аудит
близких дублей. R03/R04 частичные; пять других вопросов явно подтверждены.
Участнику B: по development отсутствие model даёт 9 FN — первый приоритет;
прототип и общие runtime-модули в этой оценке не изменялись.
Все 120 AI-меток нельзя подавать как ручной gold; поддержку отдельного
AI-reference режима evaluator не включать в текущие задачи без отдельного решения.
После просмотра AI-ответов ручная проверка также не становится независимой
разметкой автоматически — происхождение нужно сохранить в отчёте.

## Как не мешать друг другу

- Каждый берёт свою feature-ветку от одного согласованного commit, присылает
  отдельное изменение и указывает проверенные команды/результат.
- A владеет отчётом Linux-запуска, B — прототипом, C — аудитом и вопросами.
  README, PROJECT_STATUS, CLI, правила, конфигурацию и evaluator объединяет
  интегратор после согласования; не редактировать их втроём одновременно.
- `data/raw/`, `data/gold/`, `outputs/`, окружения и секреты остаются вне Git.
  Каждый получает исходные данные из разрешённого источника отдельно;
  наличие кода в Gitea не означает наличие датасетов у всех.
- Разметку, unit/color-политику и состав атрибутов ведёт Влад с Codex.
  Размеры и состояние товара пока не добавлять в текущий контракт.
- Никаких внешних LLM/API-вызовов или загрузки реальных карточек без отдельного
  согласования. Платные запросы, работа с VM и публикация здесь не разрешаются
  автоматически. Этот файл распределяет работу, а не выполняет её.

Короткий формат передачи результата: **задача → commit/ветка → изменённые файлы
→ что запущено → результат → что осталось непроверенным/нужно решить**.
