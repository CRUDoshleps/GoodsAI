## Что означает ревью в сопоставлении с кодом

### 1. Внешний ввод работает, но доказательство обобщённости слабее демонстрации

`goodsai.cli predict --input`, API `/predict` и
`scripts/release/clean_run.py --input` уже принимают пользовательский ввод.
В `clean_run.py` есть external_batch, проверка пары и input hash.
Поэтому формулировка «основная цепочка зависит от demo» не доказывает наличия
технической зависимости production predict от примеров.

Однако README начинает с packaged demo и в основном batch-примере снова
использует `src/goodsai/examples/synthetic/products.jsonl`. Это может создавать
впечатление решения под примеры. Независимая оценка каталога отсутствует;
default категории — смартфоны и чайники. Registry расширяем, но наличие
механизма не доказывает качество всех категорий.

**Действие:** QA-006 #98 проверяет внешние новые входы без доступных packaged
fixtures через настоящий CLI/HTTP; DOCS-003 #101 делает этот путь очевидным.
#35 остаётся полной матрицей официальных требований. #40 измеряет качество
и стоимость на разрешённой выборке; synthetic runner не заменяет эту оценку.

### 2. Проверка LLM существует, но есть воспроизведённый дефект границы ответа

`llm.py` содержит `parse_proposals`, поиск quote в видимом тексте, numeric/
dictionary grounding, `validate_candidate`, проверку контекста и итоговую
`validate_prediction`. Утверждение об отсутствии постпроверки целиком
не соответствует изученному main.

При этом после проверки ключей proposal код выполняет `attr not in grounded`
до проверки строкового типа. Offline provider с
`{"attributes":[{"attribute":[],"value":"Zorion","quote":"Zorion"}]}`
на выдуманном `Smartphone Zorion QX-900` воспроизводит
`TypeError: unhashable type: 'list'`. Это может сорвать обработку карточки
вместо безопасного отказа LLM; API ловит общий Exception и отдаёт 500.

**Действие:** LLM-007 #99 — строгая проверка типов и regression на CLI/API/cache.
Семантическая защита остаётся #15/#37: точный span ещё не доказывает роль числа,
принадлежность главному товару и отсутствие конфликта. Известный RED SOLUTION
в прежнем adversarial отчёте нельзя скрывать заменой expected result.

`Registry.supported` возвращает True при отсутствии spec; общая поддержка
evidence поэтому зависит от конкретного источника. Это повод проверить
единый контракт в #37, а не утверждать, что любой кандидат уже одинаково
проверен registry или что все значения обязательно должны быть закрытым enum.

### 3. Отказоустойчивость уже улучшилась, но ограничения неполны

В provider есть timeout, retries, Retry-After, circuit breaker, fallback.
Существующие тесты на 429/5xx/timeout проходят. При этом:

- `_request` вызывает `response.read()` без byte limit;
- резерв бюджета делается на логическую операцию, retries выполняются внутри
  `complete`; лимит операций не равен лимиту физических HTTP attempts;
- semaphore wait не имеет общего deadline карточки, а socket timeout не
  ограничивает сумму ожидания, retries и backoff.

Это наблюдения по коду; авария от большого ответа или фактическое превышение
суточного лимита в production не заявляются как произошедшие.
**Действие:** LLM-008 #100 — ограниченное чтение, общий deadline, прозрачный
учёт attempts и локальные failure tests. #24 отвечает за единый конфиг,
#45/#48 — за более широкие router/reliability задачи.

### 4. Оператору нужен понятный отказ и рабочая проверка

API уже возвращает `error.code/message`, отдельные 400/413/415/422/500.
Нужно объяснение действий оператора, а не ещё один формат ошибок.
README/LLM guide должны показывать review, abstain, conflict, invalid input,
timeout и отсутствие ключа. Полноценный экран с сохранением решений остаётся
#19; пакетная очередь — #50. Статическая картинка и новые тексты не закрывают UI.

## Почему могли снизиться баллы

1. **Прямое объяснение reviewer:** недостаточно доказана работа на произвольном
   вводе; это относится к крупнейшему падению покрытия.
2. **Подтверждённый риск реализации:** некорректный LLM JSON способен обойти
   безопасный fallback через TypeError. Это оправдывает исправление независимо
   от того, обнаружил ли именно его проверяющий.
3. **Гипотеза:** после появления LLM проверка уделила больше внимания его
   границам, чем прежнему rules-only пути. SHA/логи не позволяют доказать причинность.
4. **Гипотеза:** заметность demo и устаревшие статусы функций затруднили оценку.
   Исправлять нужно навигацию и доказательства, не писать обещания высокого качества.
5. Автоматическое LLM-review может различаться между прогонами. Нельзя приписать
   каждую сотую конкретному commit или обвинить автора PR без воспроизведения.
