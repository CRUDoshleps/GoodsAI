### Общее заключение организаторов

Дословный основной абзац:

> Решение в целом реализует основной сценарий извлечения и нормализации атрибутов из текстовых карточек: в коде есть пайплайн от текста до структурированных предсказаний, механизм нормализации и сохранения результатов, а также расчёт метрик по атрибутам. Работоспособность подтверждена набором тестов и открывающимся демо, но воспроизводимость комплекта артефактов и единый сценарий сборки всех обязательных выходных файлов оформлены не полностью. Техническая архитектура модульна и позволяет заменить компоненты, однако есть серьёзные замечания по зависимостям, безопасности и обработке пограничных ошибок, а также неполная автоматизация выпуска всех шести требуемых артефактов.

Остальные тезисы заключения (смысл сохранён, это конспект):

- Плюсы: работающий text→attributes; нормализация и числовая уверенность;
  много тестов; модульность; экспорт и метрики по атрибутам/категориям;
  text-only, evidence, справочники и, по мнению ревьюера, порог уверенности.
- Минусы: нет единой поставки шести артефактов; версии пакетов названы
  «по-видимому, устаревшими»; pickle в research и недостаточная защита API;
  перехват BaseException и блокировки без учёта сетевых ФС;
  нет удобной пакетной проверки и понятных оператору объяснений;
  интеграции документированы частично, нет примера production-конфигурации.

Сборщик связывает существующие результаты, не обязан автоматически писать
презентацию или заново проводить EDA. Нужен release manifest с SHA, hashes,
командами, exit codes, происхождением метрик, перечнем обязательных файлов.
При отсутствии файла — явное incomplete/failure, никакой «готовой поставки».
Публичный пакет содержит безопасную синтетику/агрегаты; реальные predictions
остаются локально или на согласованном организаторами закрытом канале.

Тесты: сборка полного synthetic fixture; missing/stale/mismatched artifacts;
несовпадение SKU входа и predictions; запрет перезаписи старого выпуска;
отсутствие gold → качество N/A; недопуск секретов/сырых данных в публичную часть.
Приёмка: одна команда повторяемо создаёт проверяемый комплект или объясняет,
какого обязательного артефакта нет. Coverage отдельно от P/R/F1.

Подготовку blind human review вести параллельно A–C. Уже обсуждавшийся validation
не становится независимым после переименования. Резерв test держать закрытым
до заморозки методов; не подбирать по нему правила, prompts и пороги.

M3 начать отдельным согласованным этапом: реальный rules→LLM→verifier путь,
сравнение с rules-only на reviewed development, версии prompt/model/config,
per-attribute/category TP/FP/FN, P/R/F1, coverage, abstain/review, latency,
число запросов, токены и стоимость. Adapter без измеренного эксперимента не
считать устранением замечания об отсутствии модельного подхода.

Использовать предоставленный организаторами шлюз, а не выбирать другой сервис
по умолчанию. Проверить доступные модели/лимит и разрешённость передачи карточек;
ключи только из env, не в документах. Сам факт наличия ключа не отменяет
согласование реальных данных/бюджета. Независимый test нужен для итоговой оценки,
не для настройки M3; не блокировать подготовку эксперимента ожиданием test-метрик.

Стоп/разбор: новые FP, потерянные TP, неверное evidence, нарушение split,
превышение бюджета, ухудшение latency сверх заранее согласованного бюджета.
Прирост баллов и качества заранее не обещать.

### E. Минимальный workflow оператора

Связь: PRODUCT-001, позже ACTIVE-001. После B, без большого UI-проекта.
Сначала локальный Markdown/HTML-отчёт: стабильный ID, поле, значение,
evidence, перевод reason code, review/abstain, пустое решение человека.
Экспорт/импорт исправлений проверяет ID и происхождение; AI-ответ не превращается
в human-reviewed без подтверждения. Экранировать HTML; реальные тексты вне Git.
Для blind test форма без predictions и AI-предзаполнения.
Тесты: round-trip, дубли/неизвестные ID, HTML, отсутствие решения человека.
Это закрывает часть замечания о ручной проверке раньше полноценного веб-интерфейса.

## 6. Что требуется от команды

- По возможности получить SHA/время фактически проверенного прогона.
- Интегратору подтвердить GitHub→Gitea процесс и распределение существующих
  задач; текущий локальный origin не перенастроен.
- Уточнить закрытый способ передачи реальных predictions и официальный API,
  когда организаторы его опубликуют; выбрать ответственного за презентацию.
- Для независимой оценки нужен человек, не видевший predictions; для M3 —
  разрешённый объём данных/бюджет. До этого внешние вызовы не делать.

Анализ, исправление документальных несоответствий, synthetic сборщик и его
локальные тесты не требуют раскрытия ключей или просмотра независимого test.
Первый рекомендуемый PR — A; следующий функциональный результат — B.
