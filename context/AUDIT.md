## Приоритетные замечания

Ниже сохранены технические замечания первичного аудита. P1/P2 описывают важность для будущей реализации; они не означают обязательность исправления всей системы до продуктового чекпоинта.

### Для финального этапа: комплект сдачи ещё не собран

Основание: [README, статус](../README.md#статус), фактический список файлов и PDF, стр. 18. Нет исходников пайплайна, зависимостей, команд запуска, EDA, результатов и финальной презентации. README существует, но не выполняет роль инструкции воспроизведения решения.

Для финала эксперт должен иметь возможность запустить извлечение и проверить метрики. Это не условие готовности текущего концептуального показа; end-to-end baseline относится к работе после обратной связи. Названия `src/`, `run_pipeline.py` в ТЗ сейчас обозначают будущие файлы.

### P1. Псевдокод правил обходит общую политику auto_accept

Основание: `IMPLEMENTATION_MASTER_PLAN.md:176–192`, особенно строки 178–180; сравнить с `TECHNICAL_SPEC.md:185–191`.

Для rule/seller-кандидата достаточно `is_grounded and is_valid`, после чего выполняется `accept`. Условие не проверяет confidence и не определяет, входит ли в `is_valid` проверка всех конфликтующих источников. Контракт `auto_accept` в ТЗ требует порог, а конфликт должен давать review.

Последствие при буквальной реализации: синтаксически допустимое совпадение может обойти защиту. Рекомендация: единый финальный gate для rules, encoder и LLM; конфликт проверяется до принятия. Вероятность из правила нельзя назначать произвольной константой и представлять как измеренную точность.

### P1. Evidence-контракт неоднозначен и пример содержит неверные координаты

Основание: `TECHNICAL_SPEC.md:81–114`. В title `Смартфон Samsung Galaxy S24 256GB Black` срез `[20:25]` равен `axy S`, тогда как `raw_value` равен `256GB`, а `evidence_text` содержит длинную другую цитату. Корректные координаты самого `256GB`: `[28:33]` при нумерации Unicode code points с нуля и исключённой правой границе.

Нет поля исходного текста (`title`, `description` или путь к seller attribute), не определена система координат, `source` смешан с понятием источника текста, а строки `rule|encoder|llm` и `auto_accept|review|abstain` являются описанием enum, не валидными значениями enum. Не описан `null` для отказа.

Последствие: нельзя надёжно проверить или подсветить evidence. Предлагаемый контракт приведён отдельно в [CONTRACT_PROPOSAL.md](CONTRACT_PROPOSAL.md).

### P1. Наличие цитаты не доказывает принадлежность атрибута товару

Основание: `TECHNICAL_SPEC.md:159–175`, а также собственный сложный пример `README.md:60–67`.

«Чехол, совместимый с Samsung» содержит Samsung, но это не доказательство бренда чехла. «Не поддерживает 5G», «8 ГБ RAM, 256 ГБ ROM», «красный кабель в комплекте» тоже дают существующие, но потенциально неверно назначенные spans. Нормализация и проверка диапазона не разрешают эти случаи.

Рекомендация: проверять связь «товар — атрибут — значение», отрицание, совместимость, комплект и альтернативные варианты; включить их в challenge-набор. Для правил использовать ограниченный контекст и явные отрицательные условия. Непроверенная семантика должна ограничивать auto_accept. Ноль предсказаний без цитаты не означает ноль ошибочных предсказаний.

### P2. План сужает допустимые решения сильнее задания

Основание: `CASE_REQUIREMENTS_TRACEABILITY.md:44–49`, `IMPLEMENTATION_MASTER_PLAN.md:279–290`, `PRODUCT_IMPROVEMENTS.md:7–16`; PDF, стр. 16.

Внутренние критерии требуют дообученный local encoder; раздел MVP включает rules → encoder → LLM. В PDF требуется начать с правил/словарей, затем попробовать ML- **или** LLM-подход. Три модели, собственный fine-tuning и работающий UI не названы обязательными артефактами.

Рекомендация: baseline + один выбранный модельный эксперимент; остальные ступени только при измеримом приросте и наличии времени. Правила могут быть первым работающим результатом, но не заменяют предусмотренную заданием попытку модельного подхода.

### P2. В псевдокоде отсутствует использование cache hit

Основание: `IMPLEMENTATION_MASTER_PLAN.md:185–192`. При `no_cache_hit == false` выполнение уходит в `review_or_abstain()`, а чтение кэшированного кандидата не описано.

Последствие при буквальной реализации: повторный запрос ухудшит результат. Сначала загрузить и проверить cached result; только при miss вызывать provider в пределах бюджета. Версии модели, схемы, нормализатора, словаря и prompt должны участвовать в валидности кэша.

### P2. Оценка и разметка требуют более строгого протокола

Основание: `TECHNICAL_SPEC.md:183–198`, `IMPLEMENTATION_MASTER_PLAN.md:49–55,100–110,208–230`.

Правильные намерения уже есть: group split, неизменный test, gold-set. Но не определены знаменатели coverage, учёт review/abstain в F1, разница между отсутствующей меткой и отрицательным примером. Temperature scaling не является универсальным калибратором regex scores, NER logits и LLM-выходов. Несколько десятков примеров подходят для диагностики, но не доказывают стабильно высокую precision на всех срезах.

Рекомендация: сначала проверить предоставленную размеченную часть; не дублировать её разметку автоматически. Разделять inputs и targets, создавать weak labels только для train. Unlabeled span не превращать автоматически в истинный O. Репрезентативный test отделить от challenge-набора и active-learning train. Разделение по SKU недостаточно, если одинаковая модель встречается у разных продавцов. Разделение по семействам и cold-start по категориям — разные проверки, их нельзя смешивать без пояснения.

Метрики считать для всех обязательных пар SKU–атрибут и отдельно для auto_accept; review не выдавать за автоматическое покрытие. Для LLM измерять прирост итогового пайплайна на полном test, а residual-срез показывать дополнительно.

### P2. Источник исследования неверно атрибутирован

Основание: `RESEARCH_AND_ARCHITECTURE.md:18,151`. У статьи Explicit Attribute Extraction in e-Commerce Search первый автор Robyn Loughnane; Shervin Malmasi — редактор сборника. Работа рассматривает поисковые запросы, а не карточки товаров. Это полезная аналогия для NER и нормализации, но перенос на задачу карточек требует проверки. [Первичный источник](https://aclanthology.org/2024.ecnlp-1.13/).

Проверка ключевых источников записана в [SOURCES.md](SOURCES.md); всю библиографию аудит не сертифицирует.

## Что уже сделано правильно

- README явно отличает планы от реализации; HTML помечен как концептуальный, числа — демонстрационные.
- Ограничение на текст соблюдено в проектном замысле.
- Нормализация, происхождение значений и отказ включены в ядро архитектуры.
- Разделены offline-метрики и гипотезы о CTR/GMV.
- Не обещан перенос чужих F1 и экономии на собственный датасет.
- План начинается с EDA и baseline, содержит защиту от утечек и оценку по атрибутам.

## Что нельзя оценить без запуска реализации и согласованного эталона

Архив уже есть, но реальную точность/полноту, качество нормализации, скорость, расход памяти, стоимость, достаточность разметки, выбор encoder против LLM и обобщение на новые категории ещё нельзя оценить. Git-проверка выполнена локально; соответствие текущему удалённому репозиторию не проверялось.
