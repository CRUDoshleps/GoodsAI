# Оценка текущего репозитория

Проверка: 14 октября 2026, commit `ba2032a`, локальная ветка main. На старте рабочее дерево чистое. Оценивается концептуальный прототип для продуктового чекпоинта, не готовность production-системы.

## Вердикт

**Вектор правильный.** Текстовое извлечение, нормализация, происхождение значений, проверка оператором и раздельные метрики атрибутов подходят задаче. В репозитории достаточно материала для обсуждения концепции. Следующая польза — связный показ одного сценария и согласованный небольшой объём.

Главный продуктовый риск — смешение четырёх направлений в одном первом MVP: помощник оператора, массовая обработка, помощь продавцу и приоритизация по спросу. Предлагается выбрать первое как ядро; сравнение — в [CONCEPTS.md](CONCEPTS.md).

## Что изменилось с прошлого аудита

Добавлены PRODUCT_CHECKPOINT_PRESENTATION.md, требования платформы, PDF и архив через Git LFS. Прежние созданные в чате файлы аудита в текущем checkout отсутствуют. Они не восстановлены поверх новой структуры: этот анализ помещён в отдельную папку context/analysis, исходные материалы context/case и context/datasets сохранены.

## Приоритетные замечания

### 1. Сценарий презентации снова расширяет MVP

Основание: PRODUCT_CHECKPOINT_PRESENTATION.md, слайды 4, 6, 10 и раздел «Что должно быть готово к демонстрации»; PRODUCT_IMPROVEMENTS.md, таблица MVP.

План одновременно включает encoder, LLM, калибровку, active learning, demand queue, seller score и экран стоимости. Скриншот текущего чекпоинта говорит о проверке концепций; перечисленные технические артефакты не подтверждены там как обязательные. Внутреннее желание команды сделать более сильное демо допустимо, но не должно выглядеть как требование организаторов.

Рекомендация: ближайший показ — одна категория, 3–5 полей и три исхода. Сложные компоненты показывать как варианты следующего этапа. Не называть score «калиброванным», пока калибровка не проведена, и не давать демонстрационному 0.98 видимость результата эксперимента.

### 2. Статус данных требует точной формулировки

Основание: README.md:135; PROJECT_CONTEXT.md, «Что пока неизвестно»; context/README.md; .gitattributes.

Данные уже переданы пользователем и предварительно изучались в этой сессии. Сейчас context/datasets/cu_ws.zip — файл-указатель размером 135 байт, не архив ZIP; внутри записаны SHA-256 и ожидаемый размер 1 156 787 524 байта. Это нормальная форма хранения Git LFS, но перед распаковкой нужен доступный LFS-объект. Его доступность на удалённом сервере не проверена.

Рекомендуемая запись статуса: «Источник датасета добавлен через Git LFS; в текущем checkout находится указатель. Есть предварительный обзор каталога, полный EDA и модельные метрики ещё не выполнены». Не утверждать ни «датасета никогда не было», ни «в этой папке уже лежит распаковываемый архив».

### 3. Слишком сильное обещание про поиск и GMV

Основание: PRODUCT_CHECKPOINT_PRESENTATION.md, главная мысль и слайд 2.

Пропуск атрибута может исключить товар из результатов соответствующего фильтра. Из этого не следует, что товар обязательно исчезает из всего поиска. Заполнение атрибута также не гарантирует рост продаж.

Рекомендация для рассказа: «помогаем повысить полноту карточек и доступность товаров в релевантных фильтрах; влияние на поиск и продажи предстоит измерить». Вывод об экономии каскада также оставить гипотезой до сравнения.

### 4. Пример нормализации в презентации неоднозначен

Основание: PRODUCT_CHECKPOINT_PRESENTATION.md:199.

Строка безусловно сводит `256GB`, `0.25 TB` и `256 Гб` к `256 ГБ`. Правила пересчёта единиц и трактовки ошибок регистра не заданы. Биты и байты нельзя молча смешивать, а перевод TB в GB требует явной принятой политики единиц.

Для прототипа использовать однозначный пример: `256GB`, `256 GB`, `256 ГБ` → `256 ГБ`. Спорные единицы отправлять на проверку; правила конверсии согласовать со справочником задания.

### 5. Контракт evidence содержит неверные координаты

Основание: TECHNICAL_SPEC.md:81–114. Для title `Смартфон Samsung Galaxy S24 256GB Black` указанный срез `[20:25]` равен `axy S`, а `256GB` занимает `[28:33]` при индексации Unicode code points с нуля, правая граница не включается.

Рекомендация: явно хранить поле-источник, способ индексации и проверять равенство исходного среза evidence. Метод извлечения (`rule`, `encoder`, `llm`) и поле карточки (`title`, `description`, seller field) — разные свойства. Существование цитаты не доказывает, что она относится к нужному атрибуту именно этого товара.

### 6. Роутер и кэш в плане не полностью согласованы

Основание: IMPLEMENTATION_MASTER_PLAN.md:176–192.

Правило принимается по grounded/valid без явного общего порога и проверки конфликтов; в условии `no_cache_hit` не показана ветка использования сохранённого кандидата. Это замечания к будущей реализации, не причина откладывать чекпоинт. Перед реализацией нужен единый gate принятия для всех источников и явная ветка cache hit.

### 7. В библиографии перепутаны автор и редактор

Основание: RESEARCH_AND_ARCHITECTURE.md:18,151. Для Explicit Attribute Extraction in e-Commerce Search правильная краткая атрибуция — **Robyn Loughnane et al., 2024**. Shervin Malmasi указан в редакторах сборника. Работа об извлечении из поисковых запросов, поэтому перенос на карточки следует обозначить как аналогию. [Первичный источник](https://aclanthology.org/2024.ecnlp-1.13/), проверен ранее в этой сессии.

### 8. Параметры каталога могут выдать готовый ответ

Основание: предварительный разбор того же архива, см. [DATA_FACTS.md](DATA_FACTS.md).

В каталоге есть прямые параметры и их `_search`-варианты. Если оценивать извлечение отсутствующего значения, оставив его или эквивалентное поле во входе, получится копирование ответа. Для демонстрационных карточек указать, какие поля скрыты/модифицированы. Для последующей оценки исключать целевой параметр и его алиасы из seller input; текстовое свидетельство в названии/описании оставлять, если именно из него нужно извлекать.

## Что сохранить

Фокус на операторе; только текст; нормализация; источники значений; конфликт и отказ; оценка по атрибутам; разделение демонстрации и реальных метрик; отсутствие обещаний конкретного роста GMV.

## Границы проверки

Выполнены локальные Git-проверки, чтение документов, проверка HTML на отсутствие script/inline event handlers, проверка LFS-указателя, сверка JSON-примера и использование уже собранных статистик архива. Не запускались обучение, полный EDA, Parquet joins и функциональные тесты извлекателя. Исходные материалы не исправлялись автоматически: замечания подготовлены для команды.
