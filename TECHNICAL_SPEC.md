20.10.2026 Владислав дополнительно передал скриншоты разделов 2–6 и сообщил,

Нормализация поддерживается общей проверкой кандидата; разрешение политики
не означает, что консервативные rules обязаны найти каждый допустимый пример.

code points, end exclusive. HTML анализируется с отображением на raw source;
цитата из скрытого текста, команды или примера ответа не доказывает факт товара.
Правила разметки — [HUMAN_GOLD_GUIDELINES](docs/HUMAN_GOLD_GUIDELINES.md).
Неизвестные оттенки/семейства и расхождения с catalog reference требуют
adjudication; P05–P11 не разрешают пересчитать старые ответы под новые predictions.

### Атрибуты продавца: разрешённый источник и незакрытая реализация

Кейс прямо разрешает исходные текстовые атрибуты продавца. Запрет всех таких
полей не является требованием организаторов. E1 пока отклоняет непустой
seller_attributes; это ограничение реализации, устраняемое отдельной DATA-002.

До включения поля нужен проверяемый mapping: исходный файл/колонка и hash,
происхождение именно от продавца до каталожного обогащения, доступность на
inference и отделение от reference/gold. Название колонки само по себе этого
не доказывает. Пока происхождение не установлено, catalog vendor/model/params,
оценочные метки и clicks не достигают Product/Extractor. Seller ID при наличии
разрешён только для отдельной оценки срезов, не как подсказка значения.
Отсутствие доказательства исключает поле, а не делает его разрешённым по умолчанию.

DATA-002 должна отдельно предложить форму seller evidence и миграцию: текущая
v0.1 разрешает evidence только title/description. Копирование params в description
для обхода ограничения запрещено. Общие normalizers/verifier, конфликты и
отрицательные leakage tests обязательны; политика не включает этот путь в runtime.

### LLM, итоговые файлы и воспроизводимость

- Наличие выданного ключа не является разрешением на произвольную отправку
  реальных карточек. По умолчанию доступны локальные проверки и synthetic
  trace в ранее разрешённом scope; в этом этапе вызовов нет. Реальный пакет
  требует явного решения команды: источник/hash, development/train scope,
  разрешённые поля, модель/шлюз и бюджет. Test reserve на этом этапе не открывается
  и не отправляется; разрешение development не распространяется на него.
  Будущая test-оценка требует отдельного решения после заморозки метода. Отдельное
  ограничение владельца данных имеет приоритет над решением команды.
- Шесть артефактов остаются обязательными. Реальные данные, разметка, predictions
  и полные логи остаются вне Git; публично — код, synthetic примеры, безопасные
  агрегаты, manifests и provenance. Секреты не публикуются даже в manifests.
- Рабочий способ подготовки полного комплекта — локальный закрытый release-
  комплект с predictions и проверенными hashes по ART-003; его можно упаковать
  в закрытый архив для передачи. Сборщик создаёт bundle, не выбирает канал доставки.
  Это политика подготовки, не утверждённый способ передачи организаторам.
  До финальной сдачи команда назначает закрытый канал/получателя и подтверждает
  допустимость состава; размещение только на VM или одних агрегатов не считается
  передачей всех шести артефактов. Неизвестный канал отмечается незакрытым release gate.
- Качество без независимого reference не называется независимым: AI-assisted
  reviewed development, catalog silver и human test указываются отдельно.
  Traffic weights используются только при документированном происхождении;
  отсутствие данных означает N/A, не придуманную оценку.

### Применение к следующим задачам

SPEC-001 завершает фиксацию рабочего контракта, не получение неизвестных ответов
организаторов. SPEC-002 может строить исполняемую матрицу подтверждённых и
командных сценариев с отдельным столбцом статуса источника. Seller inputs,
ноутбуки, реальный категорийный пилот, калибровка, передача полного комплекта и
реальный LLM benchmark остаются явно непокрытыми до своих реализаций/приёмок.
Снятие зависимости SPEC-001 не снимает DATA-001, приёмку CONF-003 или разрешение
модельного пакета/бюджета. API-001 фиксирует transport limits/errors/batch;
DATA-002 — происхождение и новую форму seller inputs; это разные задачи.

Migration: старые входы/выходы, units, decisions, scores, configs и predictions
сохраняются без изменений. Новые JSON поля или нормы equivalence требуют
отдельного решения, версии/тестов и migration notes. При появлении официального
контракта сравнить его с P01–P11, явно перечислить расхождения и реализовать
совместимый adapter либо версионированное изменение; историю не переписывать.

Диагностическое дополнение EVAL-006: отдельный offline reference
`catalog_silver`, [протокол](docs/research/silver_evaluation_protocol.md).
Он не является human gold, не меняет API/CLI result v0.1 и runtime confidence.
Catalog metadata/reference хранятся отдельно от Product; scores и пороги
калибровки не включаются в runtime без отдельного архитектурного решения.

## 1. Цель

Система получает текст карточки товара и заполняет обязательные характеристики.
Результат должен быть пригоден для поиска и фильтров, но не должен придумывать
отсутствующие факты. Для каждого значения сохраняется источник в тексте.

Главный пользователь — оператор качества каталога. Продавец получает меньше
пустых полей, покупатель лучше находит товар, бизнес сокращает ручную обработку
и измеряет стоимость заполнения одной карточки.

## 2. Область первой версии

Поддержанные категории:

| ID | Категория | Поля |
| --- | --- | --- |
| `761` | смартфоны | `brand`, `model`, `storage_gb`, `ram_gb`, `screen_inches`, `battery_mah`, `color` |
| `482` | чайники | `brand`, `model`, `capacity_l`, `power_w`, `color` |

Ноутбуки и остальные категории входят в последующее расширение. Добавление
категории выполняется через версионируемую схему, словари и тестовый набор.

## 3. Вход

Одна запись JSONL или тело `POST /predict`:

| Поле | Тип | Требование |
| --- | --- | --- |
| `schema_version` | string | сейчас только `0.1` |
| `sku_id` | string | непустой идентификатор |
| `category_id` | string/null | ключ категорийной схемы |
| `title` | string | непустой текст |
| `description` | string/null | дополнительный текст |
| `seller_attributes` | array | в E1 только пустой список |
| `source_flags` | array[string] | служебные признаки происхождения |

Запрещено передавать готовые target-поля, vendor/model из каталога, gold,
клики и иные признаки, раскрывающие ответ. Неизвестные поля отклоняются.

## 4. Выход

Для поддержанной категории возвращается запись со статусом `processed` и по
одному объекту на каждое поле схемы. Объект атрибута содержит:

- `attribute` — имя поля;
- `value` и `unit` — нормализованное значение или `null`;
- `confidence` и `confidence_kind`;
- `decision`: `review` или `abstain` по умолчанию; `auto_accept` только в явно
  включённом ограниченном пилоте CONF-005, описанном ниже;
- `method` и идентификатор правила/модели;
- `evidence`: поле, raw offsets и точный текст;
- `reason_codes` для отказа или конфликта.

Неизвестная категория получает `unsupported_category`. Валидный JSON, нарушающий
схему Product, в batch даёт `invalid_input` без остановки остальных записей;
в HTTP это 422. Повреждённый JSONL или внутренняя ошибка останавливают batch и
не публикуют частичную пару predictions/manifest поверх прежней. Внутренняя
ошибка HTTP — 500, не успешный пустой ответ. Limits и ошибки —
[RESPONSES](docs/RESPONSES.md) и [CONFIGURATION](docs/CONFIGURATION.md);
полная приёмка transport/batch остаётся API-001.

## 5. Функциональные требования

### FR-1. Предобработка

1. Инвентаризация файлов и SHA-256.
2. Проверка схем, типов, размера и идентификаторов.
3. Выбор разрешённых полей title/description.
4. Нормализация Unicode/HTML для анализа с сохранением отображения на raw span.
5. Отчёт по пропускам, длинам, категориям, дублям и проблемам join.
6. Разделение development/validation/test по группам похожих товаров.
7. Manifest с версиями источников и кодом подготовки.

### FR-2. Извлечение кандидатов

Текущий обязательный источник — правила и словари. Целевой pipeline добавляет
компактную модель или LLM для остатка. Каждый источник возвращает единый
внутренний `Candidate`: поле, значение, единицу, score, evidence и method.

### FR-3. Нормализация

- разные записи единиц приводятся к канонической форме;
- значения сравниваются со схемой и допустимыми диапазонами;
- бренд, цвет и категориальные значения проходят alias mapping;
- нормализация не создаёт число или категорию, которых нет в evidence.

### FR-4. Проверка

- raw offsets должны точно указывать на исходный текст;
- конфликт значений одного поля приводит к `abstain` или `review`;
- отрицание, «совместимо с», комплектность и характеристика другого объекта
  не принимаются как характеристика основного товара;
- неподдерживаемое поле и неверная единица отклоняются;
- один verifier применяется к rules, encoder и LLM.

Дополнение VER-002: действующий внутренний `Candidate` проверяется общим
`CandidateVerifier` до объединения для rules, LLM/cache и experimental GLiNER.
Нормализация подтверждается raw/visible evidence, служебные команды и
помеченные примеры ответа не считаются фактами товара. Структурные дефекты
внутреннего генератора остаются ошибками инварианта; недопустимые внешние
кандидаты дают фиксированный reject reason. Схема v0.1, категории, единицы,
scores, review/abstain и отсутствие auto_accept сохранены. Официальное
подтверждение #10 и развитие интерфейсов #43 этим не подменяются.
Границы и воспроизведение — [VERIFIER](docs/VERIFIER.md).

### FR-5. Маршрутизация

Конфигурация CONF-001 имеет отдельную версию `config_version=1` при неизменном
input/output `schema_version=0.1`. Полный профиль задаёт category→rule-family,
числовые bounds, heuristic scores, контекстные окна и API limits. Loader общий
для CLI/API; неверный профиль отклоняется до output/listen. Единицы и грамматика
остаются частью контракта. Production defaults прежние; изменение категории,
scores или диапазонов требует решения архитектора. Default флаги LLM/auto_accept
остаются `false`: opt-in LLM-fallback
включается отдельно (`--llm`) и использует те же bounds и окна. Детали и legacy migration — `docs/CONFIGURATION.md`.

Дополнение CONF-002 (20.10.2026, принято PR #109): совместимый профиль v1/v2
получает полный `runtime.llm` и `runtime.review_threshold=null`. Прежний профиль
без этих полей детерминированно дополняется defaults; частичная новая секция и
неизвестные параметры отклоняются. Общий resolver CLI/API применяет профиль,
разрешённые non-secret env и явные CLI overrides в этом порядке. Enabled —
отдельный opt-in, JSON-профиль сам не разрешает вызов. Ключ/URL — только env.
Auto-accept остаётся запрещён, числовой review threshold отклоняется до
калибровки; правила решений, units, scores и output v0.1 прежние. Ни нового
порогового gate, ни изменения бюджетной политики физических retries здесь нет.

Целевое решение выбирает самый дешёвый достаточный метод:

1. rules для точных шаблонов;
2. encoder или быстрая LLM для неразобранных полей;
3. сильная LLM только для конфликта/длинного хвоста;
4. `review` или `abstain`, если доказательства недостаточно.

Router должен сохранять причину маршрута, цену, latency и число вызовов. Пока
нет независимого gold, общего auto_accept нет; исключение — ограниченный
согласованный пилот CONF-005 ниже.

#### CONF-005: согласованное исключение storage-pilot-97-v1 (22.10.2026)

Владислав после проверки 145/145 предложений согласовал цель precision 97%
для opt-in пилота category=761, attribute=storage_gb. Подробный контракт,
ограничения, включение/rollback: [STORAGE_PILOT](docs/STORAGE_PILOT.md).
Профиль `runtime.auto_accept_enabled=true` требует явного `runtime.auto_accept`
с policy_version и target_precision `[0.97,1]`. Проверенная условная нижняя
95%-граница 97,955% должна достигать target; иначе кандидаты остаются review.
Сам numeric review_threshold по-прежнему запрещён.

Разрешены только memory.context.v1 / memory.title-pair.v1 в прежней области
storage-shadow-1, точное evidence, method=rule и отсутствие memory conflict.
Default config, извлекаемые значения и scores не меняются. Кандидат пилота
может получить decision=auto_accept в прежнем объекте v0.1; confidence_kind
остаётся heuristic, score не вероятность. Другие поля и LLM не получают
такого права. Изменённый extraction profile не может использовать прежний аудит.

Это явное решение пользователя о риске после результатов; исходная цель 99%
не объявляется выполненной и её отчёт не переписывается. Независимая
calibration/human gold не завершены. Пилот не даёт production-гарантий,
не пишет значения в каталог и не меняет ВМ автоматически.

### FR-6. Ручная проверка

Review-интерфейс или отчёт показывает исходный текст, подсвеченный evidence,
нормализованное значение, метод, confidence и причины. Оператор может принять,
исправить или отклонить. Его действие сохраняется отдельно от исходного ответа.

### FR-7. Воспроизводимость

Каждый batch-run создаёт predictions и manifest: Git SHA, dirty flag, hashes
входа/выхода/конфига, версии правил и словарей, Python/platform, run ID, время,
RSS, скорости, coverage, причины отказов и `llm_calls`.
CONF-002 добавляет `runtime_policy`, `runtime_policy_sha256`,
`effective_config={profile,runtime_policy}` и `effective_config_sha256` без
credentials. `config_sha256` сохраняет смысл hash базового профиля; batch run ID
учитывает effective config и code hash. API `/health` публикует два effective
hashes, сохраняя прежний временный prediction run ID и result schema v0.1.

### Подготовка политик по атрибутам — CONF-006

Отдельный offline-план `attribute-shadow-1` задаёт category/attribute/rule scope,
raw-score filter и целевую precision группы для всех 12 текущих category×field
сочетаний. Он не является runtime config и не разрешает auto_accept.
До predictions фиксируются config/plan/code hashes, после — family-balanced
selection до чтения reference. Per-field shadow coverage, catalog agreement и
human audit с границами риска разделены. Неизвестные labels, отсутствие support
и pending ответы не считаются успехом. Принятый storage-pilot-97-v1 сохраняет
свои отдельные условия; его аудит не переносится на другие поля.
Команды и ограничения: [ATTRIBUTE_SHADOW](docs/ATTRIBUTE_SHADOW.md).

## 6. Нефункциональные требования

| Область | Требование |
| --- | --- |
| Безопасность | секреты только в окружении; текст товара не пишется в operational logs |
| Стоимость | дневной и batch-бюджет; отказ от LLM после исчерпания лимита |
| Надёжность | атомарная пара predictions/manifest; запрет двух writers одного output |
| Скорость | batch и HTTP не блокируют друг друга; latency измеряется по маршрутам |
| Масштабирование | категории, пороги и модели задаются конфигурацией |
| Наблюдаемость | счётчики статусов, методов, причин отказа, latency и затрат |
| Совместимость | один schema version для CLI/API/evaluator; изменение версии явно |

## 7. Метрики приёмки

SPEC-002 `spec-002-v1`: [исполняемая матрица](docs/SCENARIO_MATRIX.md) проверяет
заявленные synthetic сценарии внешнего CLI/HTTP и offline gates, фиксирует
REQ/SCN source status и artifact hashes. Реализованный сценарий без доказательства
не проходит gate; неготовые/неизвестные требования остаются в общем отчёте.
Это не метрика качества каталога и не изменение JSON input/output v0.1.

Качество измеряется только на зафиксированной разметке:

- micro/macro precision, recall и F1;
- F1 и coverage по каждому атрибуту и категории;
- false accept rate для `auto_accept`;
- `review_rate`, `abstain_rate`, conflict rate;
- exact evidence rate;
- стоимость и LLM calls на 1 000 SKU;
- p50/p95 latency, throughput и peak RSS;
- срезы по продавцам, редким значениям, длине текста и новым категориям.

Числовые пороги выпуска задаются после EVAL-001. До этого приёмка новой модели
означает статистически и практически обоснованное улучшение на одном frozen
split без ухудшения precision критических полей.

## 8. Критерии MVP

MVP готов, когда:

1. официальный вход преобразуется в контракт без утечки target;
2. правила и хотя бы один реальный model/LLM route работают в общем pipeline;
3. каждый принятый кандидат имеет проверяемое evidence;
4. есть независимый human test и отчёт с ошибками;
5. создан полный predictions-файл и связанный manifest;
6. README воспроизводится на VM из чистого окружения;
7. API слушает `0.0.0.0:8000`, health и batch-сценарий проходят;
8. release в Gitea указывает исходный GitHub SHA и допускает rollback;
9. подготовлена финальная техническая презентация с фактическими цифрами.

## 9. Не входит в ближайший MVP

- автоматическая запись в боевой каталог;
- полноценный кабинет продавца;
- извлечение из изображений;
- обучение большой языковой модели с нуля;
- поддержка всех категорий без отдельной проверки;
- `auto_accept` на основе некалиброванного score.

### Внутренний stage contract v1 (ARCH-001)

CandidateSource.candidates(Product) возвращает Iterable[Candidate];
CandidateGate.reason(Candidate) возвращает reason или None. CategoryRegistry
определяет attributes/category, unit и normalize. Это Python-интерфейсы,
не новые поля JSON и не разрешение произвольного кода из конфигурации.
Любой внедрённый source проходит общие проверки до merge кандидатов.

Predictor.predict(Product, run_id) возвращает прежний JSON v0.1.
ValueNormalizer.normalize(category_id, attribute, value, unit) возвращает
каноническую строку либо выбрасывает ValueError. GateFactory.create(Product) создаёт
подготовленный CandidateGate. Router.select(Product, eligible) возвращает
tuple уникальных допустимых пропусков. Provider.complete принимает messages,
max_tokens и необязательные deadline/reserve_attempt, возвращает ProviderResponse.
PredictionSink.stage(output) — context manager двух staging Path: predictions
и manifest; успешный выход публикует согласованную пару, ошибка сохраняет
предыдущую. HTTP возвращает JSON напрямую, файлов не создаёт.

CLI/API собирают зависимости через composition.build_runtime. Config v1/v2 и
runtime policy v1 валидируются до работы; legacy config проходит существующую
явную миграцию. Candidate уже содержит каноническое значение: normalizer
проверяет числовое evidence в gate, source отвечает за первичную нормализацию
по тому же профилю. Внедрение компонентов разрешено доверенному Python-коду,
не JSON/env/plugin imports. Обязательные методы существующих source, поля
JSON, решения, confidence и единицы не изменены. Официальное согласование
SPEC-001 #10 остаётся отдельным условием. [Архитектура](docs/ARCHITECTURE.md).

### Opt-in категорийный реестр (кандидат CONF-003)

По поручению Тимура подготовлен отдельный train-only кандидат. Config v2
явно содержит registry v1: category → ordered catalog_* IDs → name/kind/unit/
train values/support и конечный набор изученных numeric templates. Внешняя
форма E1 JSON 0.1 сохранена; Product по-прежнему принимает только text-only.
Новые category/attribute IDs и units включаются только этим явным конфигом.
Старые labels/evaluator не мигрируют автоматически: нужен schema mapper и
архитектурное review. Default config v1 и его две категории не меняются.
Политика остаётся heuristic review/abstain, LLM/auto_accept off.
Контракт train-проекции, словарей, нормализации, evidence и границы поддержки
описаны в [CATEGORY_REGISTRY](docs/CATEGORY_REGISTRY.md). Реальный train/split,
независимые метрики и принятие расширения остаются отдельными условиями.

## Exact producer reuse (LLM-004)

Opt-in cache сохраняет producer proposals, а не решения. Fingerprint включает
exact исходные поля/flags, schema/config, prompt, generation, model/revision и
namespace; TTL не более суток. Каждый replay проходит текущий общий gate.
Single-flight не отменяет request deadline, budgets и concurrency. Формат
prediction v0.1 и review/abstain остаётся прежним; подробности — docs/EXACT_CACHE.md.

LLM-006: выключенный по умолчанию source-block planner сохраняет original offsets;
недоказанная полнота означает полный контекст, превышение budget — abstain.
Контракт prediction прежний; описание: docs/CONTEXT_PLANNER.md.

LLM-005: opt-in selector принимает только attribute/span_id|null; значение
собирается из исходного span и проходит общий gate на полном source.
Неполный индекс даёт abstain; server constrained generation не заявляется.
Подробности: docs/SPAN_SELECTOR.md.

PRODUCT-005: alias lifecycle изменяет существующий configuration dictionary
только через draft/impact/review/owner publish. Versions immutable, current
pointer CAS; rollback создаёт новую версию. Prediction snapshots/решения
не меняются задним числом. Numeric/catalog schema и semantic alias policy
не согласуются автоматически. Инструкция: docs/DICTIONARY_CONSOLE.md.
