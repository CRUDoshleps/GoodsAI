# Инструкции для людей и агентов

## Перед работой

1. Прочитать `docs/PROJECT_STATUS.md`, `TASKS.md` и документ своей области.
2. Выполнить `git status --short --branch` и `git fetch work`.
3. Выбрать одну задачу со статусом `READY`.
4. Создать ветку `<type>/<id>-<slug>` от `work/main`.
5. Поставить задачу в `IN_PROGRESS`, указать исполнителя и ветку.
6. Отдельно закоммитить и опубликовать захват: `chore(tasks): claim <ID>`.

Точный порядок labels, Issue, claim, блокировки и review описан в
`docs/TASK_MANAGEMENT.md`. У Issue должны быть один `type:*`, один
`priority:*` и один `status:*`.

Нельзя начинать реализацию, пока команда не увидит опубликованный claim.
Одновременно у задачи один владелец. Другие участники могут быть reviewer.

## Источники истины

- `TASKS.md` — работа и владельцы;
- `TECHNICAL_SPEC.md` — технический контракт;
- `docs/PROJECT_STATUS.md` — фактическое состояние;
- `docs/EVALUATION.md` — правила метрик;
- `docs/RELEASES.md` — выпуск;
- код и тесты — доказательство реализации.

Слайды, старые планы и сообщения не подтверждают наличие функции в runtime.
Если документы расходятся с кодом, исправить документ или открыть задачу.

## Границы данных

- Extractor получает только разрешённый text-only вход.
- Нельзя передавать `vendor`, `model`, готовые `params`, clicks или gold как
  подсказку и затем считать совпадение качеством извлечения.
- `data/raw/`, `data/gold/`, `outputs/`, модели, логи и секреты не коммитятся.
- Реальные карточки нельзя отправлять внешнему API без явного решения команды.
- Недоверенный pickle не загружается. Reader с флагом trusted остаётся
  изолированным исследовательским инструментом.
- Test reserve не просматривается до заморозки методов и порогов.

## Контракт результата

- Для каждого поля есть значение с evidence либо явный `abstain`.
- Evidence обязан точно совпадать с исходным title/description.
- Несколько несовместимых значений дают конфликт, а не случайный выбор.
- Confidence rules baseline — эвристический score, не вероятность.
- До калибровки все найденные кандидаты имеют `review`; `auto_accept` запрещён.
- Общая accuracy не заменяет per-attribute precision/recall/F1 и coverage.

## Работа с моделями

- Сначала фиксируется baseline и gold, затем проводится сравнение.
- LLM получает схему и минимальный контекст, возвращает structured output.
- Ответ без точного evidence отклоняется общим verifier.
- Модель, цена, latency, число вызовов и причины маршрутизации записываются.
- Нельзя добавлять encoder или LLM только ради наличия нейросети: компонент
  остаётся в pipeline только при измеримом улучшении качества/стоимости.

## Изменения и review

- Не менять `main` напрямую, не делать force push и не стирать чужую работу.
- Не смешивать рефакторинг, новую функцию и изменение метрик в одном PR.
- Новая функциональность получает проверки ошибок и отрицательные примеры.
- Изменение схемы, единиц, confidence, решений или категорий требует решения
  архитектора и обновления `TECHNICAL_SPEC.md`.
- При завершении указать команды, фактический результат и непроверенное.
- `DONE` ставит интегратор после merge; автор переводит задачу в `REVIEW`.

## Репозитории

`work` — GitHub для разработки. `release` — Gitea организаторов. Feature-ветки
сливаются в GitHub `main`; workflow автоматически fast-forward публикует этот
commit в Gitea `main`. Прямые рабочие commits в Gitea запрещены.
Секреты никогда не помещаются в URL remote, commit, PR, terminal transcript
или документацию.
